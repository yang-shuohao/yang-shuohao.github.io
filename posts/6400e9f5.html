第13章 Mask 与裁剪机制

在 UGUI 的渲染体系中，Mask 与裁剪机制是一个典型的“渲染阶段控制系统”。它既不参与 UI 的布局计算，也不负责 Mesh 的生成，而是在最终渲染阶段对像素的可见性进行约束，从而实现遮罩、局部显示与复杂视觉层级关系。

从整体架构来看，Mask 系统位于 Graphic 之后、CanvasRenderer 之前的渲染链路中，其作用是在 GPU 执行片元写入之前，对像素进行条件过滤。因此，它本质上属于渲染管线中的“像素过滤层”，而不是“几何处理层”。

在实际 UI 开发中，Mask 的使用非常广泛，例如滚动视图的可视窗口、弹窗内容裁剪、头像圆形遮罩等。但从底层实现来看，这些视觉效果的实现方式并不相同，UGUI 中主要提供了两种裁剪体系：基于 Stencil Buffer 的 Mask，以及基于矩形计算的 RectMask2D。

这两种机制在实现路径、性能特征以及适用场景上存在明显差异，也共同构成了 UGUI 裁剪系统的完整结构。

从渲染流程的角度来看，Mask 的引入会直接影响 UI 的批处理行为与 GPU 状态切换，因为裁剪本身属于渲染状态的一部分。一旦进入 Mask 体系，UI 的合批规则将不再仅仅依赖 Texture 与 Material，还需要额外考虑 Stencil 状态或裁剪区域的一致性。

因此，Mask 系统虽然在功能上属于“视觉增强模块”，但在性能层面却是一个“高影响组件”。理解其底层原理，对于 UI 性能优化与渲染问题排查具有重要意义。

本章将从 Mask 的基本原理出发，逐步分析其在 UGUI 中的实现方式，并进一步延伸到 Stencil Buffer 机制、RectMask2D 对比以及嵌套裁剪结构，最终建立对 UI 裁剪系统的完整认知框架。

13.1 Mask 原理

Mask是Unity UGUI中用于实现局部可见性控制的一种基础机制，其核心作用是在不改变UI几何结构的前提下，对子级UI的像素可见范围进行约束。换句话说，Mask并不参与顶点层面的裁剪，而是在渲染管线的片元阶段决定哪些像素最终可以写入帧缓冲。

从系统设计角度来看，UGUI的Mask是一个典型的“渲染阶段约束器”，它通过Stencil Buffer实现对像素级别的筛选，从而构建出视觉上的裁剪效果。

13.1.1 Mask的基本组成结构

在UGUI中，一个完整的Mask结构通常由两个部分构成。

第一部分是Mask自身所在的UI节点，该节点负责定义裁剪区域的形状。这个形状通常由Image组件提供，例如一张带透明通道的图片，也可以是任意UI图形。

第二部分是Mask的子节点区域，这些子节点是实际受到裁剪影响的渲染对象。在层级结构上，所有子节点都会继承Mask的裁剪规则，形成一种树状传播关系。

需要注意的是，Mask的作用范围是基于Canvas渲染层级的，而不是Transform空间意义上的父子关系。也就是说，只要在同一个UI层级下且处于Mask作用域内，就会受到裁剪影响。

13.1.2 Mask的工作方式：从“写入”到“测试”

Mask的实现可以拆解为两个关键阶段，分别是Stencil写入阶段与Stencil测试阶段。

在写入阶段，当Mask本身被渲染时，Unity会启用材质中的Stencil写入配置。此时GPU会针对Mask覆盖的像素区域，将一个指定的模板值写入Stencil Buffer。这个值通常是递增或固定的标识值，用于表示该区域属于某个Mask层级。

在测试阶段，当Mask的子节点开始渲染时，每一个片元都会读取当前像素位置的Stencil值，并与自身材质中设定的参考值进行比较。如果比较结果通过，则该像素正常写入颜色缓冲区；如果不通过，则该像素会被直接丢弃。

这一过程发生在片元着色器之后的深度/模板测试阶段，因此不会影响顶点计算，也不会影响UI的布局逻辑。

13.1.3 Mask与材质系统的关系

UGUI中的Mask并不是一个独立的渲染模块，而是通过修改材质参数来实现的。

当一个UI对象添加Mask组件后，Unity会自动替换或修改其材质的Stencil相关属性，包括：

  • Stencil ID，用于标识当前Mask层级

  • Stencil Comparison，用于定义比较规则

  • Stencil Operation，用于定义写入方式

  • Read Mask与Write Mask，用于控制参与比较的位掩码范围

这些参数最终会被编译进Shader中，在GPU执行时作为固定逻辑参与片元测试。

因此，Mask的本质并不是“代码层裁剪”，而是“Shader驱动的像素过滤规则”。

13.1.4 Mask层级与嵌套机制

UGUI允许Mask嵌套使用，这意味着一个Mask内部可以再包含另一个Mask，从而形成多层裁剪结构。

在这种情况下，每一层Mask都会递增Stencil值或使用不同的Mask ID，从而在Stencil Buffer中形成层级标记。子节点在渲染时需要同时满足多个Stencil条件，才能最终通过测试。

这种嵌套机制虽然提供了很强的表达能力，但也带来了Stencil状态管理复杂度的增加，同时会影响批处理合并效率，因为不同Stencil状态通常会导致DrawCall拆分。

13.1.5 Mask的渲染阶段位置

从Unity渲染管线来看，Mask发生在Canvas批处理之后的GPU光栅化阶段。

其整体流程可以概括为：

  1. UI顶点生成

  2. Canvas批处理与排序

  3. DrawCall提交

  4. Stencil写入（Mask对象）

  5. 片元测试（子UI对象）

  6. 像素写入帧缓冲

可以看到，Mask并不参与CPU侧的几何裁剪，也不影响布局系统，它完全属于GPU阶段的像素控制机制。

13.1.6 小结

Mask的本质是基于Stencil Buffer的像素级过滤机制，它通过“先写入标记，再进行比较测试”的方式，在GPU片元阶段实现UI可见区域控制。由于其工作发生在渲染后期，因此能够支持任意形状裁剪，但也会带来一定的性能开销与DrawCall复杂度增加问题。

13.2 Stencil Buffer 机制

Stencil Buffer是Unity UGUI实现Mask裁剪能力的底层核心机制，它本质上属于GPU渲染管线中的逐像素模板缓冲区。与颜色缓冲区用于存储像素颜色不同，Stencil Buffer用于存储每个像素的“状态标记”，并通过这些标记控制后续片元是否能够写入最终的帧缓冲。

在UGUI体系中，Stencil Buffer并不是一个可选的辅助功能，而是Mask系统能够实现任意形状裁剪的根本原因。理解Stencil Buffer的工作方式，等同于理解UGUI裁剪系统的底层执行逻辑。

13.2.1 Stencil Buffer的基本结构

Stencil Buffer通常与Color Buffer和Depth Buffer并列存在于GPU的帧缓冲结构中。每一个像素位置都会对应一个Stencil值，该值通常是一个8位或更高位宽的整数，用于记录该像素在当前渲染阶段所处的模板状态。

从数据结构上看，Stencil Buffer可以理解为一个与屏幕分辨率等大的二维数组，其中每个元素存储一个整数标记值。这个标记值不会直接影响像素颜色，但会参与后续的比较运算。

13.2.2 Stencil的写入过程

Stencil Buffer的写入发生在片元着色器之后的固定功能管线阶段。

当UI对象（例如Mask本身）被渲染时，GPU会根据其材质中的Stencil配置执行写入操作。写入过程主要由以下几个参数控制：

  • Reference Value（参考值）

  • Write Mask（写入掩码）

  • Stencil Operation（写入操作规则）

在UGUI中，Mask对象通常会设置一个固定的Reference Value，例如1或递增值。当Mask区域的像素被渲染时，GPU会对这些像素对应的Stencil Buffer位置写入该值。

写入行为并不是简单的覆盖，而是由Stencil Operation决定。例如可以是：

  • Replace（直接替换）

  • Increment（递增）

  • Decrement（递减）

  • Keep（保持原值）

UGUI默认情况下多采用Replace模式，以保证Mask区域的明确性与稳定性。

13.2.3 Stencil的测试过程

Stencil Buffer的真正作用体现在“测试阶段”。

当子UI对象开始渲染时，每一个片元都会触发Stencil测试逻辑。该逻辑在片元着色器之后执行，但在最终写入帧缓冲之前。

测试过程可以抽象为以下步骤：

  • 首先读取当前像素位置的Stencil值

  • 然后将该值与材质中的Reference Value进行比较

  • 根据Comparison Function判断是否通过

  • 如果通过，则继续执行后续深度与颜色写入

  • 如果失败，则该片元被直接丢弃

Comparison Function通常包括：

  • Equal（等于）

  • NotEqual（不等于）

  • Less（小于）

  • Greater（大于）

  • Always（始终通过）

  • Never（始终失败）

在UGUI Mask中，最常见的组合是Equal比较，即只有Stencil值匹配Mask写入值的区域才允许渲染。

13.2.4 Stencil在多层Mask中的行为

当场景中存在嵌套Mask时，Stencil Buffer会表现为一个“层级状态记录器”。

每一层Mask都会在Stencil Buffer中写入不同的值或通过掩码位进行组合，从而形成层级结构。例如：

  • 第一层Mask写入值1

  • 第二层Mask写入值2或递增1

  • 子节点需要同时满足多个Stencil条件

在这种情况下，Stencil不再只是简单的开关机制，而变成了一种“状态叠加系统”。

这种设计使得UGUI能够支持复杂的嵌套裁剪，但也带来一个问题，即Stencil状态组合越复杂，Shader变体数量越多，DrawCall切换成本越高。

13.2.5 Stencil与GPU管线的关系

Stencil测试属于固定功能管线的一部分，其执行顺序位于片元着色器之后，但在深度测试与颜色写入之前。

整体顺序可以概括为：

  • 顶点处理阶段

  • 图元装配阶段

  • 光栅化阶段

  • 片元着色器执行

  • Stencil测试

  • 深度测试

  • 颜色写入

由于Stencil测试发生在固定阶段，因此它不会受到Shader逻辑的直接影响，但会受到材质参数的间接控制。

这也是为什么UGUI可以通过修改材质属性来控制Mask行为，而无需修改Shader核心逻辑。

13.2.6 Stencil的性能特性

Stencil Buffer的使用本质上是以“额外的内存读取与比较”为代价，换取灵活的像素级裁剪能力。

在性能层面，它具有以下几个特点：

  • 不会影响顶点阶段性能

  • 会增加片元阶段的计算开销

  • 可能导致DrawCall拆分

  • 在嵌套Mask情况下开销叠加

尤其是在复杂UI结构中，如果Mask层级过多，会导致Stencil状态频繁切换，从而影响GPU批处理效率。

因此在实际项目中，Stencil Mask虽然功能强大，但通常需要与RectMask2D等更轻量的裁剪方式配合使用，以平衡性能与表达能力。

13.2.7 小结

Stencil Buffer是UGUI Mask系统的底层执行基础，它通过在像素级别记录状态值，并在片元阶段进行比较测试，实现UI区域的精确裁剪控制。其核心特点是“写入标记 + 条件测试”的双阶段机制，使得UGUI能够支持复杂嵌套遮罩效果，但同时也引入了一定的GPU开销与批处理复杂度。

13.3 对渲染流程的影响

Mask与Stencil机制并不是独立于UGUI渲染流程之外的附加功能，而是深度嵌入在Canvas渲染管线中的一组状态控制逻辑。它不仅影响像素是否可见，还会间接影响批处理合并、DrawCall拆分以及GPU状态切换方式。因此，从整体渲染流程的角度理解Mask的影响，是分析UGUI性能结构的重要一环。

13.3.1 Mask对Canvas渲染阶段的插入位置

在UGUI的标准渲染流程中，Canvas会首先完成可见UI的遍历与排序，然后进入批处理阶段，最后提交DrawCall到GPU执行。

Mask的介入点并不在CPU的布局与排序阶段，而是在DrawCall执行过程中的GPU状态阶段。具体来说，Mask相关的Stencil状态会在材质绑定时被注入到渲染管线中，从而影响后续片元测试行为。

整体流程可以抽象为：

  • UI遍历与脏标记更新

  • 布局计算与矩阵更新

  • 渲染排序（根据Sorting Layer与Order）

  • Canvas批处理（Batching）

  • 材质与Shader状态绑定

  • Mask区域Stencil写入

  • 子节点片元Stencil测试

  • GPU输出最终像素

可以看到，Mask的影响点集中在“材质状态绑定之后”的GPU阶段，而不是UI构建阶段。

13.3.2 对批处理（Batching）的影响

UGUI的批处理依赖一个关键条件，即相同材质状态与相同渲染状态的UI可以合并为一个DrawCall。

Mask机制会直接破坏这一条件。

当不同UI对象处于不同Stencil状态时，即使它们使用相同的纹理与Shader，也无法合并批次，因为Stencil Reference Value、Comparison Function等参数不同。

具体影响包括：

  • 不同Mask层级会强制拆分DrawCall

  • 嵌套Mask会增加状态切换次数

  • 同一Canvas内的UI可能被切分为多个渲染批次

  • Batch合并范围被Stencil状态限制

因此，在复杂UI结构中，Mask越多，Batch效率越低，这是Stencil机制带来的直接副作用。

13.3.3 对DrawCall结构的影响

在没有Mask的情况下，UGUI通常可以将多个UI元素合并为较少数量的DrawCall，从而降低GPU提交开销。

但引入Mask之后，DrawCall结构会发生明显变化。

可以将其理解为“按Stencil状态分组”的渲染方式：

  • 每一个Mask层级对应一个Stencil状态组

  • 每一个状态组内部可以继续进行Batch合并

  • 不同状态组之间必须拆分DrawCall

因此最终的DrawCall数量通常呈现“分段式增长”，而不是线性增长。

在嵌套Mask场景中，这种分段结构会进一步复杂化，形成多层嵌套的状态切片。

13.3.4 对GPU状态切换的影响

GPU在渲染过程中需要维护一组固定功能状态，其中Stencil状态是重要组成部分。

每当渲染一个新的Mask层级或子节点时，GPU可能需要进行以下状态切换：

  • Stencil Reference Value更新

  • Stencil Comparison Function切换

  • Stencil Write Mask调整

  • Shader Variant切换（部分情况下）

这些状态切换本身并不消耗大量计算资源，但会破坏GPU流水线的连续性，从而影响吞吐效率。

在高频UI更新场景中，例如动态列表或复杂HUD界面，这种状态切换会累积成明显的性能开销。

13.3.5 对渲染顺序与可见性的影响

Mask不仅影响性能，还会改变UI最终的可见性逻辑。

在没有Mask的情况下，UI的可见性仅由层级顺序与透明度决定。而在引入Mask后，可见性还需要满足Stencil测试条件。

这意味着一个UI元素是否可见，取决于两个条件：

  1. 是否处于正确的渲染层级

  2. 是否通过Stencil测试

这种双重约束使得UI渲染逻辑从“线性可见性模型”转变为“条件可见性模型”，从而增加了调试复杂度。

例如：

  • UI元素可能存在但完全不可见

  • UI元素被遮挡但仍参与Batch

  • UI层级正确但Stencil不匹配导致消失

这些现象在复杂UI系统中非常常见。

13.3.6 与RectMask2D的对比影响

在渲染流程影响方面，Mask与RectMask2D存在明显差异。

Mask（Stencil方式）：

  • 发生在GPU片元阶段

  • 支持任意形状

  • 影响Batch合并

  • 增加DrawCall拆分概率

  • 状态切换成本较高

RectMask2D（矩形裁剪）：

  • 发生在CPU剔除阶段

  • 基于包围盒判断

  • 不依赖Stencil Buffer

  • 对Batch影响较小

  • 性能更稳定

因此在实际项目中，RectMask2D通常用于列表与滚动区域，而Mask用于复杂形状UI，这是性能与表达能力之间的典型权衡。

13.3.7 小结

Mask与Stencil机制对UGUI渲染流程的影响主要体现在三个层面：渲染管线插入点的变化、Batch合并规则的破坏以及GPU状态切换的增加。它将原本基于材质与纹理的线性渲染模型，扩展为基于Stencil状态的分组渲染模型，从而在提升表达能力的同时引入额外的性能成本与结构复杂度。

本章小结

本章围绕UGUI中的Mask与裁剪机制展开分析，从原理层面逐步深入到GPU底层实现，并最终回到对整体渲染流程的影响。

Mask机制的核心在于Stencil Buffer的使用，它通过在像素级别写入标记值，并在后续片元阶段进行条件比较，从而实现对UI可见区域的精确控制。这种方式使得UGUI能够支持任意形状的裁剪效果，而不依赖于几何层面的顶点修改。

Stencil Buffer作为GPU固定功能管线的一部分，承担了“状态记录与条件过滤”的双重角色。在Mask写入阶段，它负责记录区域标识，在子节点渲染阶段，它负责通过比较规则决定像素是否可见。这种“写入 + 测试”的双阶段机制，是整个Mask系统能够成立的基础。

从渲染流程角度来看，Mask并不参与UI的布局计算与顶点生成，而是发生在DrawCall提交之后的片元阶段。然而，它对渲染结果的影响却是全局性的，不仅决定像素是否输出，还会改变Batch合并方式与DrawCall结构。尤其在多层嵌套Mask场景中，Stencil状态的叠加会进一步增加GPU状态切换频率，从而对性能产生明显影响。

与此同时，Mask机制在表达能力与性能之间形成了一种典型权衡。Stencil方案提供了强大的任意形状裁剪能力，但代价是更高的GPU片元开销与更复杂的批处理拆分逻辑。相比之下，RectMask2D通过CPU侧矩形剔除实现更轻量的裁剪效果，在性能上更具优势，但表达能力受到限制。

因此，在实际UI系统设计中，需要根据具体场景在Mask与RectMask2D之间进行选择，以在视觉效果与渲染性能之间取得平衡。

通过本章的分析可以明确，Mask并不是一个简单的UI组件功能，而是一个贯穿GPU渲染管线的状态控制系统。理解其底层机制，有助于更深入地掌握UGUI的渲染结构与性能特征。
