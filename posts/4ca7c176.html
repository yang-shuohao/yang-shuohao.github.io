第25章 UI 架构设计

在 UGUI 的工程实践中，UI 架构设计往往决定了系统的上限，而不仅仅是某个功能模块的实现方式。当项目规模逐渐扩大，UI 数量增加、交互复杂度提升、状态来源多样化之后，单纯依赖组件堆叠或局部优化已经无法保证系统的稳定性，此时架构层面的设计能力就会直接影响整体性能表现与开发效率。

与前面章节关注的单点机制不同，UI 架构设计更强调“整体组织方式”。它不仅涉及界面如何被创建与销毁，还涉及 UI 如何被分层管理、如何响应数据变化，以及如何在复杂交互下保持结构清晰与性能可控。

从系统角度来看，一个成熟的 UI 架构通常需要解决三个核心问题：结构如何组织、职责如何划分，以及数据如何驱动界面更新。如果这些问题在设计阶段没有被清晰定义，后续的 Layout 优化、批处理优化甚至 Canvas 优化，都只能在局部层面进行修补，而无法从根本上解决系统复杂度上升带来的性能与维护问题。

因此，本章将从 UGUI 实际工程出发，围绕 UI 架构的分层设计、模块组织方式、生命周期管理以及状态驱动模型展开分析，逐步建立一套适用于复杂项目的 UI 架构思维模型。

25.1 UI 分层与模块化

在大型项目中，UI 系统的复杂度往往随着功能增长呈指数级上升。如果缺乏清晰的结构设计，极易出现代码耦合严重、复用性差、维护成本高等问题。因此，引入“分层”与“模块化”的设计思想，是构建可扩展 UI 架构的基础。

25.1.1 分层设计的核心目的

UI 分层的本质，是将不同职责的逻辑进行隔离，使系统具备以下特性：

  1. 职责单一
    每一层只处理特定类型的问题，避免逻辑混杂。

  2. 降低耦合
    上层不依赖下层的具体实现细节，仅通过接口交互。

  3. 提高复用性
    通用逻辑可以在不同 UI 模块之间复用。

  4. 易于维护与扩展
    修改某一层的实现，不会影响整体结构。

从工程角度看，分层并不是强制的规则，而是一种“约束设计”，用于控制复杂度。

25.1.2 UI 常见分层结构

在实际项目中，UGUI 常见的分层结构可以划分为以下几层：

一、表现层（View）

负责 UI 的显示与交互，直接依赖 UGUI 组件。

其职责包括：

  1. 控制界面显示与隐藏

  2. 响应用户输入（点击、拖拽等）

  3. 更新 UI 元素（Text、Image 等）

  4. 转发事件给逻辑层

典型特点：

  1. 不包含业务逻辑

  2. 不直接操作数据源

  3. 尽量保持“被动更新”

二、控制层（Controller / Presenter）

负责 UI 与业务逻辑之间的桥梁。

其职责包括：

  1. 接收 View 的事件

  2. 调用业务逻辑（Model / Service）

  3. 更新 View 状态

典型特点：

  1. 不直接操作 UI 组件

  2. 不负责数据存储

  3. 作为中间协调者

  1. 存储数据（玩家信息、配置等）

  2. 提供数据访问接口

  3. 处理数据变更通知

  3. 可独立测试

25.1.4 模块化设计

模块化是在分层基础上的进一步抽象，其核心思想是：将 UI 拆分为“功能独立的单元”。

一个 UI 模块通常包含：

  1. View

  2. Controller

  3. 相关资源（Prefab、Sprite 等）

  4. 配置数据

  1. 高内聚
    模块内部逻辑紧密相关

  2. 低耦合
    模块之间通过接口通信

  3. 可独立加载与卸载
    支持按需加载 UI

25.1.6 模块化与 UGUI 的关系

UGUI 本身并不提供模块化机制，但其组件化设计天然支持模块划分：

  1. 每个 UI Prefab 可作为模块载体

  2. Canvas 可作为模块容器

  3. 子 Canvas 可实现局部更新

结合资源管理系统（如 Addressables），可以实现：

  1. UI 动态加载

  2. 模块按需实例化

  3. 降低内存占用

25.1.7 常见设计误区

一、View 中写大量业务逻辑

导致 UI 与逻辑强耦合，难以复用。

二、Controller 过于庞大

承担过多职责，变成“上帝类”。

三、模块边界不清晰

多个模块互相调用，形成循环依赖。

四、忽略数据层设计

所有数据直接写在 UI 中，难以维护。

25.1.8 小结

UI 分层与模块化的核心，并不在于形式，而在于“控制复杂度”。

分层解决的是职责问题，模块化解决的是结构问题。两者结合，可以构建出：

  1. 易扩展的 UI 系统

  2. 易维护的代码结构

  3. 高复用的功能模块

25.2 UI 管理系统设计

在完成 UI 分层与模块化之后，下一步需要解决的是“如何统一管理这些 UI 模块”。如果缺乏统一的管理系统，UI 的创建、销毁、层级控制、状态维护等都会变得混乱，从而导致性能问题与逻辑错误。

UI 管理系统的本质，是对 UI 生命周期与显示规则的统一调度。

25.2.1 UI 管理系统的核心职责

一个完整的 UI 管理系统通常需要承担以下职责：

  1. UI 的创建与销毁
    负责实例化 UI Prefab，并控制其生命周期。

  2. UI 的显示与隐藏
    控制界面的打开与关闭行为。

  3. UI 层级管理
    确保 UI 在正确的显示层级（如弹窗覆盖主界面）。

  4. UI 状态管理
    管理当前打开的 UI 状态，避免重复打开或冲突。

  5. 资源加载与缓存
    控制 UI 资源加载策略（同步或异步）。

  6. UI 栈管理（可选）
    支持返回、关闭栈顶界面等行为。

从架构角度看，UI 管理系统通常位于 Controller 层之上，作为全局调度入口。

25.2.2 UI 分层结构设计（显示层级）

为了控制 UI 的显示顺序，通常会对 UI 进行层级划分。一个常见的分层结构如下：

一、Background 层

用于背景 UI，例如主界面底图。

二、Normal 层

普通界面，例如功能面板（背包、任务）。

三、Popup 层

弹窗界面，例如提示框、确认框。

四、Top 层

最顶层 UI，例如引导、提示信息。

五、System 层

系统级 UI，例如加载界面、全局遮罩。

25.2.3 UI 打开与关闭流程

UI 管理系统需要统一 UI 的打开流程。一个标准流程如下：

一、打开 UI

  1. 判断 UI 是否已存在

  2. 若不存在，则加载 Prefab

  3. 实例化并挂载到对应层级

  4. 初始化（Bind、数据设置）

  5. 播放打开动画（可选）

  6. 加入 UI 管理列表或栈

二、关闭 UI

  1. 播放关闭动画（可选）

  2. 从管理列表或栈中移除

  3. 销毁或隐藏 UI

  4. 释放资源（按策略）

25.2.4 UI 缓存策略

频繁创建与销毁 UI 会带来较高的性能开销，因此需要设计合理的缓存策略。

常见策略包括：

一、完全销毁

关闭 UI 时直接销毁对象。

适用于：

  1. 使用频率低

  2. 占用内存较大

二、隐藏缓存

关闭 UI 时仅 SetActive(false)。

适用于：

  1. 高频 UI（如背包）

  2. 打开关闭频繁

三、对象池复用

通过对象池管理 UI 实例。

适用于：

  1. 动态生成 UI（列表项）

  2. 大量重复元素

常见生命周期包括：

25.2.8 UI 管理系统扩展方向

一个成熟的 UI 管理系统通常还会扩展以下能力：

  1. UI 动画统一管理

  2. UI 音效控制

  3. 多语言支持

  4. 分辨率适配

  5. 输入拦截（遮罩管理）

这些功能通常不直接耦合在 UIManager 中，而是通过子系统或组件扩展实现。

25.2.9 常见问题分析

一、UI 重复打开

未做存在性判断，导致多个实例。

二、层级混乱

未统一管理父节点，导致遮挡错误。

三、内存泄漏

UI 未正确销毁或资源未释放。

四、频繁 Rebuild

UI 频繁激活/隐藏，触发 Canvas 重建。

25.2.10 小结

UI 管理系统是 UI 架构的核心调度中心，其设计直接影响：

  1. UI 系统的可维护性

  2. 性能表现

  3. 扩展能力

一个良好的 UI 管理系统，应具备：

  1. 清晰的层级结构

  2. 完整的生命周期控制

  3. 合理的缓存与加载策略

  4. 可扩展的架构设计

在此基础上，下一节将进一步深入 UI 生命周期管理机制，从执行时序角度分析 UI 行为。

25.3 界面生命周期管理

在 UI 管理系统中，生命周期管理是保证界面行为一致性与可控性的关键。若缺乏统一的生命周期规范，不同界面之间将出现初始化混乱、重复执行逻辑、资源未释放等问题。

界面生命周期的本质，是对 UI 从“创建到销毁”的全过程进行标准化定义与调度。

25.3.1 生命周期设计的核心目标

生命周期设计的核心目标在于：

  1. 明确阶段边界
    将 UI 的不同执行阶段进行划分，避免逻辑混杂。

  2. 控制执行时机
    确保逻辑在正确的时间点执行。

  3. 避免重复初始化
    区分“一次性初始化”与“多次打开逻辑”。

  4. 统一管理资源
    在合适阶段加载与释放资源。

  5. 提高可维护性
    所有 UI 遵循统一规范，降低理解成本。

25.3.2 生命周期阶段划分

一个完整的 UI 生命周期通常包含以下阶段：

一、创建阶段（Create）

UI 实例被创建，但尚未初始化。

特点：

  1. 仅进行 GameObject 实例化

  2. 不执行业务逻辑

  3. 不访问外部数据

二、初始化阶段（Init）

执行一次性初始化逻辑。

典型操作包括：

  1. 缓存组件引用

  2. 注册事件（按钮点击等）

  3. 初始化内部结构

该阶段只执行一次。

三、打开阶段（Open）

UI 被显示时触发。

典型操作包括：

  1. 设置数据

  2. 刷新 UI 显示

  3. 播放打开动画

该阶段可能被多次调用。

四、激活阶段（Show）

UI 进入可见状态。

区别于 Open：

  1. Open 偏向逻辑初始化

  2. Show 偏向显示状态控制

在一些架构中，Open 与 Show 可以合并。

五、隐藏阶段（Hide）

UI 被临时隐藏，但未销毁。

典型操作：

  1. 停止动画

  2. 暂停逻辑

  3. 取消输入响应

六、关闭阶段（Close）

UI 被关闭，准备退出。

典型操作：

  1. 播放关闭动画

  2. 移除事件监听

  3. 保存状态（如需要）

七、销毁阶段（Destroy）

UI 被彻底释放。

典型操作：

  1. 释放资源

  2. 清理引用

  3. 取消所有外部绑定

资源加载与释放需要与生命周期匹配：

  1. Init
    加载常驻资源

  2. Open

    释放资源

  1. 避免重复加载

  2. 控制引用计数

  3. 避免内存泄漏

25.3.9 常见设计问题

一、生命周期混乱

不同 UI 使用不同逻辑，导致不可维护。

二、重复初始化

在 Open 中重复执行 Init 逻辑。

三、依赖 Unity 生命周期

使用 Start / OnEnable 导致执行顺序不可控。

四、关闭逻辑不完整

未清理事件或引用，导致异常。

25.3.10 小结

界面生命周期管理，是 UI 架构稳定运行的基础。

通过标准化生命周期，可以实现：

  1. 明确的执行流程

  2. 可控的资源管理

  3. 清晰的逻辑划分

在实际工程中，应始终遵循：

  1. 生命周期由 UIManager 驱动

  2. 不依赖 Unity 默认生命周期

  3. 严格区分各阶段职责

在此基础上，可以进一步构建复杂的 UI 状态机与动画系统，实现更加完整的 UI 架构设计。

本章小结

本章从工程实践角度出发，对 UGUI 在实际项目中的架构设计进行了系统性梳理。与前文偏重底层渲染机制不同，本章更关注如何在复杂项目中“正确地使用 UI”。

首先，在 UI 分层与模块化方面，我们明确了 UI 系统必须进行职责拆分。通过 View、Controller、Model、Service 的分层设计，可以有效降低耦合，使 UI 逻辑更加清晰。同时，通过模块化组织，将 UI 拆分为独立功能单元，使其具备高内聚、低耦合的特性，从而支持复用与扩展。

其次，在 UI 管理系统设计中，我们建立了统一的 UI 调度中心。通过对 UI 的创建、显示、层级、缓存与销毁进行集中管理，可以避免界面混乱与重复实例问题。同时，引入 UI 层级结构与 UI 栈机制，使界面切换更加规范，并提升整体交互体验。

在界面生命周期管理部分，我们进一步对 UI 的执行流程进行了标准化。通过划分 Create、Init、Open、Show、Hide、Close、Destroy 等阶段，并由 UIManager 统一驱动，可以确保 UI 行为一致且可控。生命周期的规范不仅解决了初始化混乱问题，也为资源管理、动画控制与数据更新提供了明确的时机。

综合来看，本章构建了一个完整的 UI 架构基础，其核心思想可以概括为以下几点：

一、分层解决职责问题

通过明确不同层级的职责，降低系统复杂度。

二、模块化解决结构问题

通过拆分功能单元，提高复用性与可扩展性。

三、管理系统解决调度问题

通过集中控制 UI 行为，保证系统稳定运行。

四、生命周期解决时序问题

通过标准化流程，确保逻辑执行可预测。

在实际项目中，上述设计并非固定模式，而应根据项目规模与需求进行调整。但无论如何变化，其核心目标始终一致：在保证性能的前提下，构建一个清晰、稳定且易于扩展的 UI 系统。
