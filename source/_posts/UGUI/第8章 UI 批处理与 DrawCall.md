# 第8章 UI 批处理与 DrawCall

在 UGUI 渲染体系中，批处理与 DrawCall 是影响 UI 渲染性能的核心因素。

UGUI 并不会将每个 UI 元素单独提交给 GPU，而是会先经过 Canvas 统一收集，再根据材质、纹理、Shader 以及渲染状态进行批处理，最终生成真正的 DrawCall。

批处理的目标，是尽可能减少 GPU 渲染状态切换，从而降低 CPU 提交渲染命令的开销。

在 UGUI 中，多个 UI 元素只有在渲染状态一致时，才有可能被合并到同一个 Batch 中。一旦中途出现材质变化、纹理切换、Mask、Stencil 或裁剪状态变化，系统就必须中断当前批处理，并生成新的 DrawCall。

因此，很多 UI 性能问题的本质，并不是 UI 数量过多，而是 DrawCall 数量过高。

例如：

- 一个 Mask 可能导致后续 UI 无法继续合批 

- 不同图集会直接产生新的 DrawCall 

- 材质切换会中断整个 Batch 链 

- 顶点数量过大还可能触发 Mesh 拆分 

这些问题最终都会直接影响 CPU 渲染开销。

理解 UGUI 的批处理机制，是 UI 性能优化中最核心的部分之一。只有真正理解 DrawCall 的生成过程，才能准确定位 UI 渲染中的性能瓶颈。

## 8\.1 批处理原理

在进入 UGUI 合批规则与 DrawCall 生成机制之前，首先需要明确一个基础问题：**UI 批处理到底在系统中处于什么位置，它解决的是什么层级的问题。**

从整体渲染流程来看，UI 从生成到最终显示在屏幕上，需要经历多个阶段，包括 UI 数据构建、Mesh 生成、渲染状态组织以及 GPU 提交。在这一整条链路中，批处理并不负责“生成 UI”，也不负责“绘制 UI”，它的作用发生在中间阶段——即将已经生成好的 UI 渲染数据进行重组与优化。

因此，批处理可以被理解为 UI 渲染管线中的“整理与压缩阶段”。

### 8\.1\.1 批处理的基本概念

UI 批处理（Batching）的本质，是将多个独立的 UI 渲染请求合并为尽可能少的 GPU DrawCall，从而降低 CPU 与 GPU 之间的通信与状态切换成本。

在 UGUI 渲染体系中，每一个 Image、Text 或 Graphic，从逻辑上看都对应一个独立的渲染单元。如果不进行任何合并处理，这些 UI 将逐个生成 DrawCall 并提交到 GPU。

从 GPU 的执行模型来看，它并不理解 UI 结构，只接受渲染指令。每一个 DrawCall 都意味着一次完整的渲染状态提交，包括：

- 顶点数据 

- 索引数据 

- 材质状态 

- Shader 状态 

- 纹理绑定状态 

因此，DrawCall 本质上是 GPU 渲染管线的一次完整切换。

在这种模型下，如果 UI 完全独立渲染，那么 CPU 会持续不断地发起 DrawCall，导致渲染开销迅速上升。

而 UI 系统的特点在于“数量多、单体轻、状态相似”。这种结构决定了它天然适合进行合并优化。

也正是在这个背景下，批处理机制被引入到 UGUI 中。

批处理的核心思想可以概括为：**在 CPU 侧提前识别可合并的 UI，并将其统一组织为更大的渲染单元，从而减少 DrawCall 数量。**

在这一过程中，UI 不再以“单个元素”为单位提交，而是以“批次”为单位提交。

### 8\.1\.2 批处理的目标与性能意义

在理解了批处理的基本概念之后，需要进一步明确它在系统设计中的目标。

UGUI 引入批处理机制的核心目标并不是优化 UI 结构本身，而是优化渲染提交过程。

在现代渲染管线中，CPU 的瓶颈往往来自 DrawCall 的数量，而不是单个 DrawCall 的成本。每一次 DrawCall 都意味着：

- CPU 构建渲染命令 

- 渲染状态切换 

- GPU pipeline 重新绑定资源 

- 提交执行 

这些操作的代价远高于简单的顶点数据处理。

UI 系统的特殊性在于，它通常由大量小规模元素组成，例如按钮、文本、图标等。如果不进行合批处理，这些元素会形成大量独立 DrawCall，从而导致 CPU 压力快速上升。

因此，批处理机制的目标可以归纳为两个方面：

1. 减少 DrawCall 数量

2. 降低渲染状态切换频率

从系统设计角度来看，这是一种典型的“CPU 换 GPU 性能”的优化方式。

通过在 CPU 端增加一定的计算与整理成本，换取 GPU 端更高效的执行效率。

### 8\.1\.3 UGUI 批处理执行流程与合并机制

UGUI 的批处理发生在 Canvas 的 BuildBatch 阶段，这是 UI 渲染流程中非常关键的一步。

在进入该阶段之前，系统已经完成以下工作：

- Graphic 组件生成 Mesh 数据 

- CanvasRenderer 收集渲染信息 

- UI 元素完成排序（基于深度与层级） 

这些步骤完成后，UI 已经具备了“可渲染数据”，但还未进入最终提交阶段。

此时系统会进入批处理流程，对所有 UI 渲染单元进行统一判断与合并。

#### 一、批处理的基本判断条件

UGUI 是否能够合批，本质上取决于渲染状态是否一致。

主要判断条件包括：

- Material 是否一致 

- Texture 是否一致 

- Shader Pass 是否一致 

- Stencil 状态是否一致 

- 渲染参数是否一致 

这些条件共同构成了“渲染状态一致性”。

只有当所有条件完全匹配时，UI 才具备合批基础。

此外，还必须满足一个重要条件：渲染顺序必须连续。

如果中间插入了一个状态不同的 UI，那么当前批次就必须被拆分。

#### 二、Mesh 合并的实现方式

在满足合批条件的情况下，UGUI 会将多个 UI 的 Mesh 数据进行拼接。

具体过程如下：

首先，将多个 CanvasRenderer 的顶点数据依次写入同一个顶点缓冲区。

随后，将索引数据按顺序追加，并通过调整 index offset 来保证几何结构的正确性。

在这个过程中，每一个 UI 的 Mesh 不再是独立存在，而是被重新组织为同一个连续 Mesh 的一部分。

从数据结构角度来看，这本质上是一次线性数据重排过程。

#### 三、批处理机制的设计特点

UGUI 的批处理并不是一个复杂的全局优化算法，而是一种基于规则的线性判断机制。

它具有以下特点：

1. 不进行跨帧或全局范围的最优合并计算

2. 仅基于当前渲染顺序进行判断

3. 优先保证运行时性能稳定性

4. 避免复杂算法带来的额外 CPU 开销

这种设计方式的核心目标不是追求理论最优，而是保证在真实运行环境中的可预测性能表现。

#### 四、性能意义总结

从整体来看，批处理机制的性能价值主要体现在两个方面。

1. 通过减少 DrawCall 数量降低 CPU 提交压力

2. 通过减少渲染状态切换降低 GPU pipeline 开销

因此，在 UI 性能优化中，批处理能力往往比单纯的 UI 数量更关键。

很多时候，UI 数量并不直接决定性能瓶颈，而是 DrawCall 的拆分方式决定最终表现。

## 8\.2 UGUI 合批规则

UGUI 的合批机制本质上并不是“尽可能合并”，而是在严格规则约束下进行的确定性判断系统。

系统不会主动计算最优合并路径，也不会进行跨路径重排优化，而是按照固定规则逐个判断 UI 是否可以进入同一批次。

从设计目标来看，这套规则只服务于一个核心原则：**在保证渲染结果完全一致的前提下，尽可能减少 DrawCall 数量。**

因此，任何可能影响最终像素输出的差异，都会被视为合批中断条件。

### 8\.2\.1 合批规则的整体结构

UGUI 的合批规则可以抽象为四个层级约束：

1. 材质与纹理一致性约束 

2. 渲染状态一致性约束 

3. 层级与顺序连续性约束 

4. Mesh 与结构兼容性约束 

只有当四个层级同时满足时，UI 才具备进入同一批次的条件。

在 Canvas\.BuildBatch 阶段，系统会按照渲染顺序逐个遍历 UI，并基于上述约束进行连续性判断。

### 8\.2\.2 材质与纹理一致性规则

材质一致性是合批的第一层判断条件，也是最基础的约束。

只有当两个 UI 使用完全相同的 Material 时，才具备进入同一批次的可能性。

这里的“相同”不仅仅指引用相同，还包括：

- Shader 类型一致 

- Render Pass 一致 

- 关键参数一致 

如果材质不同，即使 UI 结构完全一致，也会直接导致合批中断。

与材质紧密关联的是纹理一致性规则。

在 UGUI 中，绝大多数 UI 都依赖 Texture 进行采样，例如 Sprite Atlas 或 Font Atlas。

如果两个 UI 使用不同 Texture，即使 Material 相同，也无法合批。

其根本原因在于 GPU 渲染模型中：同一 DrawCall 无法在不中断状态的情况下切换纹理绑定。

因此，纹理不同必然意味着不同批次。

### 8\.2\.3 渲染状态一致性规则

渲染状态一致性是影响合批的第二层核心约束。

该规则主要包括以下内容：

- Blend Mode（混合模式） 

- Stencil 状态 

- Shader Keywords 

- ColorMask 与渲染开关 

只要其中任意一项发生变化，就会导致当前批次被中断。

其中最典型的案例是 Mask 系统。

Mask 会引入 Stencil Buffer 的写入与读取状态变化，使得同一层级 UI 在渲染过程中产生不同状态，从而破坏合批连续性。

### 8\.2\.4 Canvas 层级与顺序连续性规则

Canvas 是 UGUI 批处理的边界单位。

不同 Canvas 之间的 UI 无法进行合批，这是因为 Canvas 本身代表一套独立的渲染上下文。

在同一个 Canvas 内，还必须满足一个关键条件：渲染顺序必须连续。

UGUI 的合批是基于“顺序扫描”的线性过程，如果中间插入一个不满足条件的 UI，将会导致当前批次立即终止，并开启新的批处理。

例如：在一组连续 Image 中，如果中间插入一个使用不同材质的 Text，那么批处理会在该位置被切断，从而形成两个 DrawCall。

### 8\.2\.5 Mesh 与结构兼容性规则

除了渲染状态之外，Mesh 结构本身也可能影响合批结果。

在大多数标准 UI 中，Mesh 都是可拼接的规则矩形结构，因此不会影响合批。

但在以下情况下可能出现合批中断：

- 自定义 Graphic 生成非标准 Mesh 

- 顶点结构发生额外变换 

- 特殊 UI 效果修改顶点数据结构 

虽然这种情况相对较少，但在复杂 UI 或特效 UI 中仍然需要注意。

### 8\.2\.6 合批规则的执行机制

在 Canvas\.BuildBatch 阶段，UGUI 会按照渲染顺序逐个遍历 CanvasRenderer。

每遍历一个 UI，就会执行一次规则判断：

1. 是否满足材质一致性 

2. 是否满足纹理一致性 

3. 是否满足渲染状态一致性 

4. 是否满足顺序连续性 

5. 是否满足 Mesh 兼容性 

一旦任意条件不满足，当前批次立即结束，并重新开始新的批处理链路。

### 8\.2\.7 设计思想与性能意义

UGUI 的合批规则本质上是一套“确定性约束系统”。

它的设计目标并不是追求理论最优的合批结果，而是：

- 保证每一帧行为稳定 

- 控制 CPU 计算复杂度 

- 避免动态优化带来的不确定性 

这种设计使得 UGUI 的性能表现具有高度可预测性，即使在复杂 UI 场景下也不会出现突发性计算开销。

### 8\.2\.8 小结

UGUI 合批规则的核心可以概括为三个关键点：

- 状态一致性决定是否可以合并

- 顺序连续性决定是否可以延续批次

- 结构兼容性决定是否可以拼接 Mesh

只有同时满足这三类条件，UI 才能被合并为同一个 DrawCall。

## 8\.3 批处理失效原因

在理解 UGUI 的合批规则之后，接下来需要进一步分析另一个更重要的问题：**为什么 UI 会失去合批能力。**

在实际项目中，开发者遇到的性能问题，很多时候并不是因为 UI 数量过多，而是因为批处理频繁失效，导致 DrawCall 数量急剧增加。

所谓批处理失效，本质上是指原本可以被合并到同一 DrawCall 的 UI，因为某些条件变化而被系统强制拆分为多个渲染批次。

这种现象通常不会影响最终显示结果，但会直接增加 CPU 的渲染提交压力。

从底层逻辑来看，批处理失效并不是异常情况，而是 UGUI 合批规则正常工作的结果。

当 UI 不再满足“渲染状态一致性”条件时，系统就必须终止当前 Batch，并重新开启新的渲染分组。

### 8\.3\.1 材质变化导致的批处理失效

材质变化是最常见的批处理失效原因之一。

UGUI 的合批建立在 Material 完全一致的基础上。一旦两个 UI 使用不同材质，即使纹理、Mesh 以及层级完全相同，也无法进入同一个批次。

例如：

- 使用不同 Shader 

- 使用不同 Material 实例 

- Material 参数发生变化 

都会导致批处理被中断。

其中一种非常隐蔽的情况是运行时材质实例化。

当代码修改 material 属性时，Unity 往往会自动复制一个新的 Material 实例。例如：

```C#
image.material.color = Color.red;
```

此时虽然视觉效果只是颜色变化，但底层已经不再共享同一个 Material，因此原有合批会立即失效。

这也是 UI 性能优化中非常典型的隐藏问题。

### 8\.3\.2 纹理变化导致的批处理失效

除了 Material 之外，Texture 也是决定合批的重要条件。

在 GPU 渲染过程中，同一个 DrawCall 无法在不中断状态的情况下切换纹理绑定。

因此：只要 Texture 不同，就一定无法合批。

在 UGUI 中，常见的纹理拆批来源包括：

- 不同 Sprite Atlas 

- 不同 Font Atlas 

- 动态加载纹理 

- RawImage 使用独立 Texture 

例如：两个 Image 即使使用同一个 Material，只要 Sprite 来自不同图集，就会生成不同 DrawCall。

因此，图集管理实际上也是 UI 性能优化的重要组成部分。

### 8\.3\.3 渲染状态变化导致的批处理失效

渲染状态变化是另一类非常重要的拆批来源。

这里的“渲染状态”不仅仅是材质本身，还包括：

- Blend Mode 

- Stencil 状态 

- Shader Keywords 

- ColorMask 

- Render Queue 

这些状态一旦发生变化，就意味着 GPU 渲染管线需要重新配置，因此系统必须开启新的 DrawCall。

其中最典型的案例就是 Mask 系统。

Mask 在底层会引入 Stencil Buffer 的写入与读取操作，这会导致 UI 渲染状态发生变化。

例如：

- Mask 本身负责写入 Stencil 

- 子节点负责读取 Stencil 

- Mask 外部 UI 不参与该状态 

因此，Mask 区域内部与外部通常无法合批。

如果界面中大量嵌套 Mask，就会导致 DrawCall 数量迅速增加。

### 8\.3\.4 Canvas 边界导致的批处理失效

Canvas 是 UGUI 批处理的天然边界。

不同 Canvas 之间的 UI 不会参与同一批处理流程，因此也无法合批。

即使两个 UI：

- 使用相同 Material 

- 使用相同 Texture 

- 具有完全一致的渲染状态 

只要它们位于不同 Canvas 中，系统仍然会生成独立 DrawCall。

这是因为每个 Canvas 都拥有独立的：

- Batch 构建流程 

- Mesh 缓冲 

- 排序体系 

- 渲染提交阶段 

因此，Canvas 的拆分本身就是一种 DrawCall 拆分。

这也是为什么在 UGUI 优化中，通常不建议过度拆分 Canvas。

### 8\.3\.5 渲染顺序中断导致的批处理失效

UGUI 的合批并不是全局搜索，而是基于渲染顺序进行线性扫描。

因此，即使两个 UI 满足所有合批条件，只要中间插入了一个不满足条件的元素，也会导致批处理链被中断。

例如：

```C#
Image A
Image B
Text
Image C
Image D
```

假设：

- A、B、C、D 使用相同 Material 

- Text 使用不同 Font Material 

那么最终会形成：

```Plain Text
Batch 1 → A + B
Batch 2 → Text
Batch 3 → C + D
```

这说明合批不仅要求状态一致，还要求渲染顺序连续。

### 8\.3\.6 顶点结构变化导致的批处理失效

在标准 UI 中，大多数 Mesh 都是规则矩形，因此通常不会因为 Mesh 结构而拆批。

但在以下情况下可能出现问题：

- 自定义 Graphic 

- 特殊 UI 特效 

- 顶点动画 

- 非标准 Mesh 拓扑 

如果不同 UI 的顶点结构无法安全拼接，系统也会终止当前 Batch。

虽然这种情况相对较少，但在复杂 UI 特效系统中较为常见。

### 8\.3\.7 批处理失效的执行机制

批处理失效发生在 Canvas\.BuildBatch 阶段。

系统会按照渲染顺序遍历所有 CanvasRenderer，并逐个检查：

1. Material 是否一致 

2. Texture 是否一致 

3. Render State 是否一致 

4. 渲染顺序是否连续 

5. Mesh 是否可兼容 

只要任意条件不满足，系统就会：

1. 结束当前 Batch 

2. 提交当前 DrawCall 

3. 开启新的批处理分组 

因此，DrawCall 的生成过程，本质上是“连续状态链不断被打断”的过程。

### 8\.3\.8 批处理失效的性能本质

很多开发者容易误认为DrawCall 增加意味着 GPU 压力变大。

实际上，在 UI 系统中，更明显的压力往往来自 CPU。

因为 DrawCall 的增加意味着：

- 更多渲染命令构建 

- 更多状态切换 

- 更多命令提交 

- 更多 CPU 与 GPU 同步 

因此，批处理失效本质上是 CPU 调度成本的增加。

尤其是在移动平台上，这类问题会更加明显。

### 8\.3\.9 小结

从整体来看，UGUI 批处理失效的核心原因可以归纳为四类：

1. 材质不一致 

2. 纹理不一致 

3. 渲染状态不一致 

4. 结构与边界限制 

而从更底层的角度来看，所有拆批问题最终都可以归结为一句话：GPU 渲染状态发生了变化。

理解这些批处理失效来源，对于 UI 性能优化具有决定性意义。

因为真正高性能的 UI，并不是“UI 数量少”，而是“批处理连续性高”。

## 8\.4 DrawCall 生成机制

在前面的章节中，我们已经分析了：

- UGUI 如何进行批处理 

- 合批规则如何工作 

- 哪些因素会导致批处理失效 

而这些内容最终都会汇聚到同一个结果：DrawCall 的生成。

因此，要真正理解 UGUI 的渲染性能，就必须进一步理解一个 DrawCall 究竟是如何产生的。

### 8\.4\.1 DrawCall 的本质

DrawCall 是 GPU 渲染流程中的基本执行单位。

它代表一次完整的渲染命令提交。

在一次 DrawCall 中，CPU 会向 GPU 提交当前需要绘制的：

- 顶点数据 

- 索引数据 

- 材质状态 

- Shader 状态 

- 纹理资源 

- 渲染参数 

GPU 在接收到这些数据后，才会正式开始执行绘制流程。

因此，从底层角度来看DrawCall 本质上是一次 GPU 渲染上下文的建立与执行过程。

在 UGUI 中，所有批处理机制的最终目标，都是尽可能减少 DrawCall 数量。

因为每一次 DrawCall 都意味着：

- CPU 构建渲染命令 

- GPU 切换渲染状态 

- 渲染管线重新绑定资源 

这些操作都会产生明显的性能开销。

### 8\.4\.2 DrawCall 在 UGUI 中的位置

很多开发者容易误认为 DrawCall 是在 Graphic 阶段生成的，实际上并不是。

Graphic 负责的只是：

- 顶点生成 

- Mesh 构建 

- UI 数据准备 

真正的 DrawCall 生成，发生在 CanvasRenderer 提交之后，渲染管线执行之前。

因此，DrawCall 位于“CPU 数据组织”与“GPU 实际绘制”之间。

从整体执行链路来看，UGUI 的渲染流程如下：

```Plain Text
Graphic
    ↓
VertexHelper
    ↓
Mesh
    ↓
CanvasRenderer
    ↓
Canvas.BuildBatch
    ↓
Batch 数据生成
    ↓
DrawCall 生成
    ↓
Render Pipeline
    ↓
GPU 执行
```

在这个过程中Graphic 不负责 DrawCall，Canvas 不直接执行 DrawCall，真正提交 DrawCall 的是渲染管线阶段。

### 8\.4\.3 DrawCall 的生成流程

在 UGUI 中，一个 DrawCall 的生成大致可以分为三个阶段：

1. 批次确定 

2. 渲染状态绑定 

3. 渲染命令提交 

#### 一、批次确定阶段

批次确定发生在 Canvas\.BuildBatch 阶段。

在这一阶段，系统已经完成：

- UI 排序 

- 合批规则判断 

- Batch 分组 

系统会根据：

- Material 

- Texture 

- Shader 

- Render State 

等条件，将多个 UI 组织为若干独立 Batch。

此时每一个 Batch，实际上已经对应未来的一个 DrawCall。

但这些数据仍然只是 CPU 侧的逻辑结构，并未真正提交给 GPU。

#### 二、渲染状态绑定阶段

在批次确定之后，系统会进入渲染状态绑定阶段。

这一阶段的核心目标是构建 GPU 所需的完整渲染上下文。

CanvasRenderer 会将当前 Batch 的：

- Mesh 

- Material 

- Texture 

绑定到渲染系统中。

在底层实现中，Unity 会完成以下操作：

- 绑定 Vertex Buffer 

- 绑定 Index Buffer 

- 激活 Shader Program 

- 设置 Render State 

- 绑定 Texture Sampler 

- 上传 Shader 常量参数 

这些操作共同组成一次完整的 GPU 渲染状态。

需要特别注意渲染状态变化，是 DrawCall 被拆分的根本原因。

只要：

- Material 改变 

- Texture 改变 

- Shader Pass 改变 

- Blend State 改变 

系统都必须重新建立新的渲染上下文，而这就意味着新的 DrawCall 被生成。

#### 三、渲染命令提交阶段

在渲染状态准备完成之后，系统会正式进入命令提交阶段。

此时，Unity 会将当前 Batch 转换为底层 Graphics API 调用。

例如：

- DirectX 

- OpenGL 

- Metal 

- Vulkan 

无论使用哪种图形 API，其底层都会对应一次类似：

```Plain Text
DrawMesh
DrawIndexedPrimitive
DrawElements
```

这样的绘制调用。

Unity 会将这些调用封装为内部渲染命令，并加入 Render Queue，由渲染线程统一调度执行。

至此，一个完整 DrawCall 正式生成。

### 8\.4\.4 DrawCall 的内部组成

从数据结构角度来看，一个 DrawCall 本质上由三部分组成。

#### 一、几何数据

几何数据用于描述“绘制什么”。

主要包括：

- Vertex Buffer 

- Index Buffer 

其中：

- Vertex Buffer 用于存储顶点信息

- Index Buffer 用于描述三角形拓扑结构

#### 二、渲染状态

渲染状态用于描述“如何绘制”。

主要包括：

- Material 

- Shader Pass 

- Blend Mode 

- Depth State 

- Stencil State 

这些状态决定 GPU 如何计算最终像素颜色。

#### 三、资源引用

资源引用用于描述“绘制时使用什么资源”。

主要包括：

- Texture 

- Shader 常量 

- Uniform Buffer 

这些资源会参与 Shader 运算。

### 8\.4\.5 DrawCall 的性能本质

很多开发者容易误认为 DrawCall 的成本来自 GPU 绘制。

实际上，在 UI 系统中，更大的成本往往来自 CPU。

因为每一个 DrawCall 都意味着：

- CPU 构建命令 

- 渲染线程同步 

- GPU 状态切换 

- Driver 调度 

尤其是在移动平台上，CPU 往往比 GPU 更容易成为瓶颈。

因此，即使每个 DrawCall 绘制内容非常简单，只要数量过多，依然会产生明显性能问题。

这也是为什么 UGUI 的所有优化手段，本质上都围绕“减少 DrawCall”展开。

例如：

- Batch 合并 

- Material 共享 

- Sprite Atlas 

- Font Atlas 

- Mask 优化 

其最终目标都是减少 DrawCall 生成次数。

### 8\.4\.6 UGUI 的分层设计思想

从系统架构角度来看，DrawCall 的生成机制体现了 UGUI 的分层设计思想。

UGUI 本身并不直接操作底层 Graphics API。

它只负责：

- 生成 UI 数据 

- 构建 Batch 

- 提供渲染信息 

而真正的 DrawCall 构建与执行，则交给 Unity 渲染管线统一处理。

这种设计具有几个明显优势：

1. UI 系统与图形 API 解耦

2. 可以兼容不同 Render Pipeline

3. 可以统一跨平台渲染行为

因此，无论是 Built\-in Pipeline、URP 还是 HDRP，UGUI 的上层逻辑都基本保持一致。

### 8\.4\.7 小结

DrawCall 是 UI 渲染流程最终在 GPU 侧执行的基本单位。

它由：

- Batch 数据 

- 渲染状态 

- GPU 资源 

共同构成。

从生成流程来看：

- Batch 决定 DrawCall

- 状态变化拆分 DrawCall

- 渲染管线最终提交 DrawCall

而从性能角度来看 DrawCall 数量，本质上反映的是 CPU 渲染提交压力。

因此，理解 DrawCall 的生成机制，是理解整个 UGUI 性能体系的核心基础。

## 8\.5 顶点限制与 Mesh 拆分

在前面的内容中，我们已经分析了：

- 材质如何影响合批 

- 渲染状态如何导致拆批 

- DrawCall 如何生成 

但在 UGUI 的批处理体系中，还存在另一类非常重要的限制：顶点数量限制。

很多开发者会认为只要材质、纹理以及渲染状态一致，UI 就一定能够持续合批。

实际上并不是，即使所有合批条件全部满足，当批次中的顶点数量超过系统允许范围时，UGUI 仍然会强制拆分 Mesh，并生成新的 DrawCall。

因此，顶点限制实际上是 UGUI 批处理体系中的“物理容量上限”。

### 8\.5\.1 顶点限制的来源

顶点数量限制并不是 UGUI 自身定义的规则，而是来自底层图形 API 与 GPU 数据结构的约束。

在渲染过程中，Mesh 需要通过 Index Buffer 来描述三角形拓扑结构。

而在 Unity 的默认实现中，索引通常使用 16 位无符号整数（ushort）存储。

其最大值为：

$2^{16}-1=65535$

这意味着单个 Mesh 默认最多只能引用 65535 个顶点。

一旦超过这一范围，索引将无法正确表示顶点位置。

因此系统必须使用 32 位索引或者拆分 Mesh。

### 8\.5\.2 为什么 UGUI 默认选择拆分 Mesh

理论上，Unity 支持使用 32 位索引格式。

例如：

```Plain Text
mesh.indexFormat = IndexFormat.UInt32;
```

这样可以突破 65535 顶点限制。

但在 UGUI 中，系统默认并不会优先采用这种方案，而是选择拆分 Mesh。

其原因主要包括以下几个方面。

#### 一、移动平台兼容性

早期移动 GPU 对 32 位 Index Buffer 支持较差。

部分设备甚至完全不支持大规模 UInt32 Mesh。

因此，为了保证跨平台稳定性，UGUI 默认采用更安全的 16 位索引结构。

#### 二、GPU 内存与带宽成本

32 位索引相比 16 位索引会增加一倍索引缓冲区大小。

这意味着：

- 更高显存占用 

- 更高带宽消耗 

- 更高缓存压力 

对于 UI 系统而言，这种收益通常并不划算。

#### 三、降低单次渲染压力

过大的 Mesh 会导致：

- 顶点缓冲区过大 

- GPU Cache 命中率下降 

- 单次 DrawCall 负载过重 

因此，即使理论上可以继续合并，也未必意味着性能更好。

UGUI 的设计思想更偏向稳定性优先。

### 8\.5\.3 Mesh 拆分的执行过程

Mesh 拆分发生在 Canvas\.BuildBatch 阶段。

在批处理过程中，系统会不断将多个 CanvasRenderer 的数据追加到当前 Batch 中。

与此同时，还会持续统计：

- 当前顶点数量 

- 当前索引数量 

当系统检测到继续合并将超过顶点上限时，就会立即终止当前 Batch。

随后：

1. 提交当前 Mesh 

2. 生成新的 Batch 

3. 开启新的 Mesh 缓冲区 

因此 Mesh 拆分本质上是一种容量边界保护机制。

其核心目标并不是优化性能，而是保证 Mesh 数据合法。

### 8\.5\.4 Mesh 拆分与 DrawCall 的关系

需要特别注意 Mesh 拆分并不等于合批失败。

即使拆分后的多个 Mesh：

- 使用相同 Material 

- 使用相同 Texture 

- 使用相同 Render State 

它们依然属于“逻辑连续批次”。

但由于 GPU 无法在一次 DrawCall 中绘制多个独立 Mesh，因此每一个拆分后的 Mesh，最终都会对应一个新的 DrawCall。

例如：一个大型 ScrollRect 列表中，所有 Item 使用完全相同的材质与图集。

理论上它们具备完全合批条件。

但如果总顶点数量超过上限，系统仍然会：

```Plain Text
Batch 1 → Mesh A
Batch 2 → Mesh B
Batch 3 → Mesh C
```

最终生成多个 DrawCall。

因此顶点限制决定的是“单个批次的最大容量”。

### 8\.5\.5 UGUI 中顶点数量的增长来源

很多开发者容易低估 UI 顶点增长速度。

实际上，一个简单 UI 往往会生成比预想更多的顶点。

例如：

- 一个普通 Image 通常包含 4 个顶点 

- 一个 Text 往往包含大量字符顶点 

- Outline 会额外复制顶点 

- Shadow 会进一步增加顶点数量 

- 富文本可能导致复杂 Mesh 拆分 

尤其是在 TextMeshPro 或复杂富文本场景中，顶点增长速度会非常明显。

例如：

```Plain Text
1000 个字符
≈ 4000 顶点
Outline
≈ 20000 顶点
```

因此大型 UI 列表非常容易触发 Mesh 拆分。

### 8\.5\.6 Mesh 拆分的性能影响

顶点限制带来的性能问题主要体现在两个方面。

#### 一、DrawCall 数量增加

这是最直接的影响。

每一次 Mesh 拆分，都会生成新的 DrawCall。

因此，即使所有状态完全一致，仍然可能因为容量问题产生额外提交。

#### 二、CPU 合并成本上升

在批处理过程中，系统需要：

- 持续检测容量 

- 动态拆分 Batch 

- 创建新的 Mesh Buffer 

这些操作都会增加 CPU 侧的构建开销。

在复杂 UI 场景中，如果频繁触发拆分，批处理效率会明显下降。

#### 三、GPU Cache 利用率下降

连续 UI 被拆分为多个独立 Mesh 后 GPU 需要频繁切换 Vertex Buffer。

这会降低：

- Vertex Cache 命中率 

- Buffer 连续读取效率 

从而进一步影响渲染性能。

### 8\.5\.7 实际开发中的优化方式

为了避免频繁触发 Mesh 拆分，实际项目中通常会采用以下优化手段。

#### 一、合理拆分 Canvas

不要将所有 UI 全部放入同一个超大 Canvas。

适当拆分：

- 静态区域 

- 动态区域 

- 列表区域 

可以有效控制单批次容量。

#### 二、控制 ScrollRect 内容规模

大型列表是最容易触发顶点爆炸的区域。

通常需要结合：

- 虚拟列表 

- 循环复用 

- 分页加载 

降低同时存在的 UI 数量。

#### 三、减少 UI 特效

Outline、Shadow 等效果会显著增加顶点数量。

尤其是在文本场景下，顶点膨胀会非常明显。

#### 四、优化富文本

复杂富文本：

- 会增加字符拆分 

- 会增加材质切换 

- 会增加顶点数量 

因此需要控制文本复杂度。

### 8\.5\.8 小结

顶点限制与 Mesh 拆分机制，是 UGUI 批处理体系中的硬性容量边界。

它决定了单个 Batch 最多能够容纳多少顶点数据。

当容量超过限制时，即使所有合批条件全部满足，系统仍然必须拆分 Mesh，并生成新的 DrawCall。

因此合批成功并不意味着 DrawCall 一定减少。

因为真正决定 DrawCall 上限的，不仅是渲染状态一致性，还有 Mesh 的物理容量限制。

## 8\.6 动态合批与静态合批差异

在 Unity 的渲染体系中，合批机制通常被划分为两种类型：

- 动态合批（Dynamic Batching） 

- 静态合批（Static Batching） 

虽然 UGUI 主要依赖自身的 Canvas 批处理系统，但理解这两种底层合批模型，对于理解 UI 批处理的设计思想仍然非常重要。

因为从本质上看 UGUI 的 Batch 系统，本身也是一种特殊形式的动态合批。

因此，本节将从底层渲染模型出发，分析动态合批与静态合批之间的核心差异，并进一步理解为什么 UGUI 会选择动态批处理作为核心方案。

### 8\.6\.1 动态合批的基本原理

动态合批（Dynamic Batching）的核心特点是运行时实时合并。

在渲染过程中，Unity 会在每一帧绘制前，对满足条件的小型 Mesh 进行临时合并，从而减少 DrawCall 数量。

其核心流程如下：

```Plain Text
多个小 Mesh
    ↓
运行时合并
    ↓
生成临时 Batch
    ↓
提交 DrawCall
```

在这一过程中，系统会根据：

- Material 

- Shader 

- 顶点数量 

- 变换状态 

等条件判断对象是否可以合并。

只有满足所有规则时，Unity 才会在当前帧临时构建合批结果。

因此动态合批本质上是一种“运行时 Mesh 重组机制”。

### 8\.6\.2 动态合批的特点

动态合批最大的优势在于灵活。

它能够适应：

- 动态移动 

- 动态显示隐藏 

- 实时变换 

- 动态内容更新 

因此特别适合频繁变化的对象。

但与此同时，它也存在明显缺点。

由于动态合批需要在运行时持续计算，因此会产生：

- CPU 顶点转换开销 

- Batch 重建开销 

- 临时缓冲区构建开销 

因此，动态合批本质上是“CPU 换 DrawCall”。

尤其是在对象数量极大时，动态合批本身也可能成为性能负担。

### 8\.6\.3 动态合批的限制条件

为了控制运行时开销，Unity 对动态合批设置了严格限制。

例如：

- 顶点数量不能过大 

- 必须使用相同 Material 

- Shader 必须兼容 

- 顶点属性数量有限 

- 不支持复杂 Multi\-Pass 

如果对象复杂度超过限制，系统就会自动放弃动态合批。

因此动态合批更适用于“小型且简单”的对象。

对于大型复杂 Mesh，其收益往往低于计算成本。

### 8\.6\.4 静态合批的基本原理

与动态合批不同，静态合批（Static Batching）的核心思想是预计算。

它不会在运行时实时合并对象，而是在：

- 编辑阶段 

- 场景加载阶段 

提前将多个 Mesh 合并为一个大 Mesh。

其执行流程如下：

```Plain Text
多个静态 Mesh
    ↓
预先合并
    ↓
生成大型 Mesh
    ↓
运行时直接提交
```

因此，静态合批几乎不需要运行时计算。

这也是它与动态合批最大的区别。

### 8\.6\.5 静态合批的特点

静态合批最大的优势在于运行时成本极低。

由于合并结果已经提前生成，因此运行阶段几乎不需要：

- Mesh 重建 

- 顶点转换 

- Batch 动态计算 

这会显著降低 CPU 压力。

因此，静态合批特别适合：

- 建筑 

- 地形 

- 固定场景 

- 不会移动的装饰物 

但它同样存在明显限制。

由于 Mesh 已经被提前合并，因此对象：

- 不能随意移动 

- 不能频繁变化 

- 不适合动态系统 

同时，静态合批通常会增加：

- 内存占用 

- Mesh 数据规模 

- 场景资源体积 

因此，静态合批本质上是一种“空间换时间”的优化方案。

### 8\.6\.6 动态合批与静态合批的核心差异

从系统设计角度来看，动态合批与静态合批最大的区别在于计算时机不同。

动态合批：运行时实时计算。

静态合批：运行前提前计算。

因此，两者实际上代表两种完全不同的优化思路。

#### 一、动态合批

特点包括：

- 灵活性高 

- 适应动态变化 

- CPU 开销较高 

- Batch 每帧可能重建 

适合：动态对象系统。

#### 二、静态合批

特点包括：

- 运行时开销低 

- 渲染稳定 

- 内存占用较高 

- 不适合动态变化 

适合：静态场景系统。

### 8\.6\.7 UGUI 为什么不使用静态合批

理解了两种合批机制后，就可以进一步理解为什么 UGUI 不采用静态合批。

其根本原因在于 UI 天然是动态系统。

例如：

- 按钮状态变化 

- 文本内容变化 

- 列表滚动 

- 动态动画 

- 界面切换 

- Layout 重建 

这些行为都会持续改变 UI 结构。

因此，UI 很难在运行前得到稳定的最终 Mesh。

如果采用静态合批，那么每次 UI 变化都需要重新生成整个大 Mesh，这显然是不现实的。

因此，UGUI 最终选择完全基于运行时动态 Batch 构建。

### 8\.6\.8 UGUI 的 Batch 本质上是什么

从行为特征来看，UGUI 的 Canvas 批处理实际上更接近增强型动态合批。

它具有几个典型特点：

1. 运行时实时构建 Batch

2. 根据 Dirty 状态动态重建

3. 基于渲染状态进行合并

4. 支持动态 UI 更新

因此，UGUI 本质上是一个专门为 UI 场景定制的动态 Batch 系统。

它并不是直接复用 Unity Renderer 的 Dynamic Batching，而是实现了自己独立的 Batch 管线。

### 8\.6\.9 UGUI 动态批处理的优化策略

由于 UGUI 依赖动态批处理，因此系统必须尽可能降低运行时重建成本。

为此，UGUI 引入了多个优化机制。

例如：

- Canvas 分层 

- Dirty 局部刷新 

- Graphic 重建分离 

- Batch 缓存 

- RenderOrder 排序 

这些机制共同作用，减少每帧需要重新构建的范围。

因此，UGUI 的性能优化，本质上是在“动态性”与“重建成本”之间寻找平衡。

### 8\.6\.10 小结

动态合批与静态合批最大的区别，在于计算发生的时机不同。

动态合批依赖运行时实时计算，更适合动态系统。

静态合批依赖预计算结果，更适合稳定场景。

而 UGUI 由于天然具有：

- 高频变化 

- 实时交互 

- 动态布局 

等特征，因此最终选择了基于 Canvas 的动态批处理体系。

它本质上是一种专门为 UI 场景设计的增强型动态合批方案，用于在灵活性与性能之间取得平衡。

## 本章小结

本章围绕 UGUI 的批处理与 DrawCall 机制展开，从渲染性能的核心瓶颈出发，系统分析了 UI 如何从大量离散的渲染单元，被逐步整合为有限数量的 GPU 提交指令。

批处理的本质，是在 CPU 侧对渲染数据进行重组与合并，通过统一 Material、Texture 与渲染状态，将多个 UI 元素压缩为同一个 DrawCall，从而降低渲染提交开销。这一机制构成了 UGUI 性能优化的基础。

在合批规则部分，可以看到 UGUI 对“状态一致性”有非常严格的约束。材质、纹理、渲染状态以及 Canvas 边界，共同决定了 UI 是否可以进入同一批次。任何一个条件不满足，都会导致批处理中断。

批处理失效原因进一步揭示了 DrawCall 增加的真实来源。材质实例化、纹理切换、Stencil 状态变化以及 Canvas 拆分，都会破坏原有合批结构，使原本连续的渲染序列被切割为多个独立批次。

在 DrawCall 生成机制中，可以看到 UI 渲染最终是如何从 CPU 数据结构，转化为 GPU 执行指令的。CanvasRenderer 在其中承担了状态封装与提交的角色，使 Mesh、Material 与 Texture 被统一打包为一次渲染调用。

顶点限制与 Mesh 拆分则从几何层面定义了合批的物理边界。即使满足所有逻辑合批条件，也可能因为顶点数量上限而被强制拆分，从而引入额外 DrawCall。

最后，通过动态合批与静态合批的对比，可以更清晰地理解 UGUI 的设计取舍。UGUI 并未采用静态预合批方案，而是基于运行时动态批处理机制，在灵活性与性能之间取得平衡，以适应 UI 高度动态化的特性。

总体来看，本章揭示了 UI 渲染性能的核心规律：DrawCall 并非由 UI 数量决定，而是由渲染状态变化频率决定。理解这一点，是进行 UI 性能优化的关键前提。
