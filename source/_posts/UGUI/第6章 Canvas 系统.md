# 第6章 Canvas 系统

在 UGUI 的整体架构中，Canvas 是连接 UI 数据与渲染管线的核心枢纽。从系统分层的角度来看，它处于 UI 渲染流程的最上游组织层，同时也是最终提交渲染数据的关键节点。

如果说 Graphic 系统负责生成可被渲染的几何数据，那么 Canvas 系统则负责对这些数据进行统一组织、批处理以及提交。它并不直接产生图形内容，却决定了这些内容如何被整合并送入 GPU 执行绘制。

Canvas 的引入，使 UGUI 从“单个 UI 元素的独立渲染”，转变为“整体 UI 系统的统一调度”。所有 UI 元素都必须依附于某个 Canvas 才能参与渲染流程，而 Canvas 也因此成为 UI 渲染真正意义上的入口。

从职责上来看，Canvas 主要承担以下三个方面的核心功能。

一、组织 UI 层级结构

Canvas 负责管理其下所有 UI 元素的层级关系，并参与排序规则的确定。这一过程直接影响最终的渲染顺序。

二、控制渲染方式

Canvas 决定 UI 的渲染模式，包括屏幕空间覆盖模式、相机空间模式以及世界空间模式。这一选择将影响 UI 的坐标体系、深度关系以及与场景的交互方式。

三、执行批处理与渲染提交

Canvas 会在运行时收集所有 Graphic 组件生成的 Mesh 数据，并根据材质、纹理以及渲染状态进行合批处理。最终，将整理后的数据统一提交给底层渲染管线，生成实际的 DrawCall。

与其他系统相比，Canvas 最重要的特性在于其“批量处理能力”。UI 的更新过程虽然分别由 Graphic 系统与 Layout 系统完成，但最终的渲染提交始终以 Canvas 为单位进行。这种设计显著提升了渲染效率，同时也使得 Canvas 的划分粒度成为性能优化中的关键因素。

从系统结构的角度来看，Canvas 可以被理解为 UGUI 渲染管线中的“汇聚层”。它将分散的 UI 元素进行统一整合，并在渲染阶段完成数据的收敛与优化，是 UI 从 CPU 数据走向 GPU 绘制的核心桥梁。

此外，Canvas 还与分辨率适配系统（CanvasScaler）以及子 Canvas 机制紧密协作，共同决定 UI 在不同分辨率设备以及复杂层级结构下的表现效果。

本章将围绕 Canvas 的核心职责展开，逐步分析其渲染模式、更新机制、批处理流程以及多 Canvas 组织策略，从整体层面深入理解 UGUI 渲染系统的最终执行结构，并为后续源码分析奠定基础。

## 6\.1 Canvas 的职责与架构

Canvas 是 UGUI 渲染体系中的核心组织单元，它位于 UI 数据生成与最终渲染提交之间，承担着统一管理与批量输出的关键职责。所有 UI 元素必须依附于 Canvas 才能参与渲染流程，因此可以将 Canvas 理解为 UI 渲染管线的入口节点。

从整体设计上看，Canvas 不仅是一个组件，更是一个负责调度 UI 渲染的系统层。它将分散在各个 UI 元素中的渲染数据进行统一收敛，并在合适的时机完成批处理与提交，从而形成最终的绘制指令。

### 6\.1\.1 Canvas 的核心职责

从职责角度来看，Canvas 的作用可以概括为三个方面。

一、层级组织

Canvas 作为 UI 树的根节点，负责管理其下所有 RectTransform 与 Graphic 组件。UI 的层级结构不仅决定了布局系统的计算顺序，同时也直接影响渲染顺序。

在渲染阶段，系统会基于 Transform 层级对所有 UI 元素进行排序。层级越靠后的节点，其渲染顺序越靠前，从而实现视觉上的覆盖关系。这一机制是 UI 正确显示的基础。

二、渲染控制

Canvas 决定 UI 的渲染模式与空间归属。通过不同的 Render Mode，UI 可以被映射到不同的坐标体系中。

在屏幕空间覆盖模式下，UI 直接绘制到屏幕，不依赖相机；在相机空间模式下，UI 参与相机的投影计算；在世界空间模式下，UI 作为三维对象存在于场景中。

这一设计使 UGUI 同时具备传统界面系统与三维场景 UI 的表达能力。

三、批处理与渲染提交

Canvas 是所有 UI 渲染数据的最终汇聚点。Graphic 组件生成的 Mesh 数据不会直接提交给渲染管线，而是先交由 Canvas 统一收集。

在收集过程中，系统会根据材质、纹理以及渲染状态对这些数据进行合批处理。合批的结果将显著减少 DrawCall 数量，从而提升渲染性能。

最终，Canvas 会将整理后的数据转换为底层渲染指令，并提交给 GPU 执行绘制。

### 6\.1\.2 Canvas 的系统架构

从架构角度来看，Canvas 并不是孤立存在的，它依赖多个模块协同完成整个渲染流程。

一、Graphic 组件

Graphic 是 UI 渲染数据的生产者。每一个 Graphic 组件负责生成自身的顶点数据与材质信息，并通过 CanvasRenderer 进行提交。

二、CanvasRenderer

CanvasRenderer 是连接单个 UI 元素与 Canvas 的桥梁。它负责接收 Graphic 生成的 Mesh 数据，并维护与渲染相关的状态信息。

可以将 CanvasRenderer 理解为“单元素渲染节点”，每一个 UI 元素通常对应一个 CanvasRenderer。

三、Canvas

Canvas 负责对多个 CanvasRenderer 的数据进行整合。它不会直接关心单个元素的生成过程，而是关注整体数据的组织、排序与批处理。

因此，Canvas 更像是一个“渲染调度中心”，负责将分散的数据整合为高效的绘制指令。

四、CanvasUpdateRegistry

CanvasUpdateRegistry 负责管理 UI 的更新流程，包括布局重建与图形重建。所有需要刷新的 UI 元素都会在这里被统一调度。

当更新完成后，相关数据才会进入 Canvas 的渲染阶段。

### 6\.1\.3 Canvas 的数据流与执行流程

从数据流的角度来看，UGUI 的渲染过程可以划分为三个阶段。

第一阶段是数据生成

Graphic 组件根据自身状态生成顶点数据，并通过 CanvasRenderer 进行缓存。

第二阶段是更新与重建

当 UI 发生变化时，系统会通过 CanvasUpdateRegistry 标记相关元素，并在更新阶段执行布局与图形重建。

第三阶段是批处理与提交

Canvas 在渲染阶段统一收集所有 CanvasRenderer 中的数据，并执行批处理。随后，将合批后的数据提交给底层渲染管线，生成最终的 DrawCall。

这一流程体现了典型的“先分散生成，再集中处理”的设计思想，有效平衡了灵活性与性能。

### 6\.1\.4 排序体系与渲染顺序

为了保证 UI 的正确显示，Canvas 维护了一套完整的排序体系。

排序的影响因素主要包括以下几个方面。

一、层级顺序

Transform 层级决定基础的渲染顺序。

二、Sorting Layer

用于在多个 Canvas 之间进行分组排序。

三、Order in Layer

用于控制同一层内的精确排序。

这些因素共同作用，决定了 UI 在最终渲染阶段的绘制顺序。

### 6\.1\.5 小结

Canvas 是 UGUI 渲染体系中的核心调度节点。它既负责组织 UI 层级与控制渲染模式，又负责整合 Mesh 数据并执行批处理与提交。

从系统设计角度来看，Canvas 体现了集中式渲染管理的思想。它将分散的 UI 渲染数据统一收敛，并通过排序与合批机制生成高效的绘制指令，是连接 CPU 侧 UI 数据与 GPU 渲染流程的关键桥梁。

## 6\.2 渲染模式

Canvas 的渲染模式决定了 UI 在场景中的空间归属以及进入渲染管线的方式，是 UGUI 中最基础且最重要的配置之一。不同的渲染模式，本质上定义了 UI 与屏幕空间、相机以及三维世界之间的关系。

在 UGUI 中，Canvas 提供三种渲染模式：Screen Space \- Overlay、Screen Space \- Camera 以及 World Space。这三种模式在坐标体系、渲染流程以及参与渲染管线的方式上存在本质差异。

### 6\.2\.1 渲染模式的本质

从底层实现角度来看，所谓“渲染模式”，本质上是决定 UI 数据在何时、以何种方式进入渲染管线。

可以将三种模式统一抽象为三个问题：

- UI 是否依赖 Camera

- UI 是否参与场景深度计算

- UI 在渲染管线中的执行阶段

Overlay 模式完全绕过 Camera，直接在最终阶段绘制；Camera 模式依附于指定摄像机，在其渲染流程中执行；World Space 模式则作为普通几何体参与完整的三维渲染流程。

这一差异决定了它们在性能、表现力以及使用场景上的不同。

### 6\.2\.2 Screen Space \- Overlay

Screen Space \- Overlay 是最常用的 UI 渲染模式。在该模式下，UI 直接绘制在屏幕空间之上，不依赖任何 Camera。

所有 UI 元素基于屏幕分辨率进行布局，其坐标体系与屏幕像素一一对应。无论场景中摄像机如何变化，UI 都始终稳定地覆盖在最终画面之上。

从渲染流程来看，Overlay 模式的 UI 会在所有摄像机完成渲染之后统一执行绘制。这意味着它不参与任何深度测试，也不会受到视角、投影或后处理效果的影响。

由于省去了 Camera 相关的计算与状态切换，该模式具有最低的渲染开销，同时也最稳定可靠。因此，它非常适用于 HUD、菜单界面以及纯屏幕信息展示等场景。

需要注意的是，Overlay 模式的 UI 无法与 3D 物体产生遮挡关系，也无法参与后处理效果，这是其功能上的限制。

### 6\.2\.3 Screen Space \- Camera

Screen Space \- Camera 模式在表现形式上仍属于屏幕空间 UI，但其渲染过程依赖于指定的 Camera。

在该模式下，Canvas 会构建一个与屏幕对齐的平面，并通过 Camera 的投影矩阵将 UI 映射到该平面上。UI 的位置仍以屏幕为参考，但其渲染过程嵌入到 Camera 的渲染流程中。

这种模式的关键特性在于，它允许 UI 参与 Camera 的深度排序与渲染效果。例如，UI 可以与 3D 物体产生遮挡关系，也可以受到后处理效果的影响。

从渲染管线角度来看，UI 会在指定 Camera 的渲染阶段中插入执行，其顺序受到 Camera 深度、Sorting Layer 以及 Order in Layer 的共同影响。

相比 Overlay 模式，该模式引入了额外的矩阵计算与渲染状态切换，因此性能开销略高。但它在表现力上更为灵活，适用于需要与场景交互的界面系统。

### 6\.2\.4 World Space

World Space 模式将 Canvas 完全转化为三维世界中的一个普通对象。此时，UI 不再属于屏幕空间，而是直接存在于世界坐标系中。

在该模式下，RectTransform 的单位从像素转换为世界单位。UI 元素可以像普通物体一样进行移动、旋转与缩放，并受到透视投影的影响。

从渲染流程来看，World Space UI 会作为普通几何体参与场景渲染，执行完整的深度测试、裁剪以及光栅化流程。其排序完全依赖深度缓冲与渲染队列。

由于进入完整的三维渲染管线，该模式的性能开销通常最高，但同时也提供了最强的空间表现能力。它常用于三维交互界面，例如角色头顶血条、世界提示信息以及沉浸式 UI。

### 6\.2\.5 渲染流程差异分析

从渲染管线执行阶段来看，三种模式的差异可以总结如下：

- Overlay 模式在所有场景渲染结束后执行

- Camera 模式嵌入到指定摄像机的渲染过程中

- World Space 模式作为普通物体参与整个渲染流程

这一差异直接决定了 UI 是否参与深度测试、是否受到后处理影响，以及是否与场景产生交互。

### 6\.2\.6 排序机制差异

不同渲染模式下，UI 的排序规则也存在明显差异。

Overlay 模式主要依赖 Canvas 层级以及 Order in Layer

Camera 模式同时受到 Camera 深度与 Canvas 排序控制

World Space 模式则完全依赖三维空间中的深度关系

理解排序机制对于避免 UI 遮挡错误与层级混乱具有重要意义。

### 6\.2\.7 性能特征对比

从性能角度来看，三种模式的开销通常呈现如下关系：

- Overlay 模式开销最低

- Camera 模式次之

- World Space 模式开销最高

这种差异主要来源于是否参与 Camera 渲染流程以及是否执行完整的三维管线。

需要强调的是，性能不仅取决于渲染模式本身，还与 Canvas 数量、批处理情况以及 UI 更新频率密切相关。

### 6\.2\.8 小结

Canvas 渲染模式的本质，是对“UI 所处空间及其渲染路径”的定义。Overlay 强调屏幕覆盖，Camera 强调与视图绑定，而 World Space 则强调空间存在。

理解三种模式在渲染管线中的位置差异，是掌握 UGUI 渲染机制与进行性能优化的基础。

## 6\.3 Canvas 更新机制

在 UGUI 的整体执行流程中，Canvas 不仅是渲染数据的汇聚点，同时也是 UI 更新流程的最终收敛节点。UI 的所有变化，都会在经过重建与整理之后，由 Canvas 统一完成渲染提交。

前文已经分析过，UI 的更新由 CanvasUpdateRegistry 统一调度，而 Canvas 则是这一调度机制的最终承载与执行环境。从系统协作关系来看，Canvas 更新机制正是连接“UI 数据更新”与“渲染管线提交”的关键环节。

### 6\.3\.1 更新机制的整体结构

从整体流程来看，UGUI 的更新可以划分为两个层面。

一、数据更新

由 Dirty 标记驱动，触发 Layout 与 Graphic 的重建过程。

二、渲染提交

由 Canvas 负责，将已经完成重建的数据整理并提交至渲染管线。

Canvas 更新机制位于这两个阶段之间，负责将“已完成的数据”转换为“可执行的渲染指令”。

需要强调的是，Canvas 并不参与 UI 的具体计算过程，而只处理最终结果。这种职责划分，使得系统结构更加清晰，同时也提高了执行效率。

### 6\.3\.2 帧循环中的执行时序

在 Unity 的帧循环中，Canvas 更新并不是一个独立的系统，而是嵌入在整体渲染流程中的。

从时序上看，一帧内 UI 的执行流程大致如下：

第一阶段，Dirty 标记

当 UI 属性发生变化时，相关组件会被标记为需要更新。

第二阶段，重建调度

CanvasUpdateRegistry 在特定阶段触发更新流程，依次执行 Layout 重建与 Graphic 重建。

第三阶段，Canvas 收敛

当所有重建完成后，Canvas 开始收集其下所有 CanvasRenderer 中的数据。

第四阶段，渲染提交

Canvas 对收集到的数据进行批处理，并生成最终的 DrawCall，提交至 GPU。

从这一流程可以看出，Canvas 的执行时机始终位于“所有 UI 重建完成之后、渲染执行之前”。它处理的是一个已经稳定的数据集合，而不会参与任何中间计算过程。

这一设计保证了 UI 渲染结果的一致性，并避免了在渲染阶段出现数据不完整的问题。

### 6\.3\.3 Canvas 的数据收集与触发机制

在更新阶段结束后，Canvas 会遍历其下所有 CanvasRenderer，收集已经准备好的 Mesh 与材质数据。

需要注意的是，这些数据在 Graphic 重建阶段已经生成完成，Canvas 并不会重新计算顶点信息，而只是进行组织与整合。

Canvas 的更新具有明显的“按需触发”特性。

如果在某一帧中，没有任何 UI 被标记为 Dirty，那么不会发生 Layout 重建，也不会发生 Graphic 重建，Canvas 也不会执行额外的批处理与提交操作。

这种按需更新机制，是 UGUI 在运行时保持高性能的重要基础。

### 6\.3\.4 多 Canvas 的更新隔离

在多 Canvas 结构中，每一个 Canvas 都拥有独立的更新边界。

当某个 Canvas 下的 UI 发生变化时，只会触发该 Canvas 的相关更新流程，而不会影响其他 Canvas。这种隔离机制，使得 UI 系统可以通过合理拆分 Canvas 来控制更新范围。

例如，将频繁变化的 UI 与静态 UI 分离到不同 Canvas，可以有效减少整体重建成本。

需要注意的是，Canvas 的拆分虽然可以降低更新范围，但也可能增加 DrawCall 数量，因此需要在更新成本与渲染成本之间进行权衡。

### 6\.3\.5 批处理触发条件

Canvas 在执行渲染提交之前，需要判断是否需要重新构建批处理数据。

常见的触发条件包括：

- 顶点数据发生变化

- 材质或纹理发生变化

- UI 层级结构发生变化

- Canvas 排序或渲染状态发生变化

当这些条件满足时，Canvas 会在下一帧执行批处理重建，并重新生成 DrawCall。

这一过程正是后续 BuildBatch 所处理的核心内容。

### 6\.3\.6 系统协作关系

从系统协作角度来看，Canvas 更新机制可以理解为一条清晰的责任链：

- Dirty 标记负责描述“需要更新什么”

- CanvasUpdateRegistry 负责决定“何时更新”

- Canvas 负责执行“如何提交渲染”

三者之间形成了一个完整的调度闭环。

这种分层设计，使 UGUI 在保持灵活性的同时，也具备较高的执行效率。

### 6\.3\.7 小结

Canvas 更新机制本质上是 UI 渲染流程的收敛阶段。它不参与数据的生成，而是对所有更新结果进行统一整理，并在渲染前完成最终的提交准备。

理解这一机制，对于分析 Canvas\.BuildBatch、优化 UI 更新性能以及合理拆分 Canvas 结构具有重要意义。

## 6\.4 Canvas\.BuildBatch 解析

在 Canvas 的更新机制中，真正决定 UI 渲染性能的关键步骤，是批处理构建过程。其中最核心的执行入口，就是 Canvas\.BuildBatch。

该过程负责将分散的 UI 渲染数据整理为可提交的批次，并最终生成 DrawCall，是 UI 从“多个独立渲染单元”转变为“高效批量渲染”的核心阶段。

从系统定位来看，BuildBatch 处于 UI 渲染流程的最末端，是所有数据准备完成后的最终整理与输出步骤。

### 6\.4\.1 BuildBatch 的整体职责

Canvas\.BuildBatch 的核心职责可以概括为三个方面。

一、收集渲染数据

从所有 CanvasRenderer 中提取已经生成的 Mesh、材质与纹理信息。

二、执行合批规则

根据渲染状态对数据进行排序、分组，并决定哪些元素可以合并。

三、生成绘制指令

将整理后的批次转换为底层渲染管线可执行的 DrawCall。

这一过程本质上是一次“数据收敛与重组”，其输出结果将直接决定 GPU 的执行效率。

### 6\.4\.2 执行流程分解

从执行过程来看，BuildBatch 可以拆分为多个连续阶段。

一、数据收集阶段

Canvas 会遍历其下所有有效的 CanvasRenderer，读取每个 UI 元素的顶点数据、材质以及纹理信息。

需要注意的是，这些数据在 Graphic 重建阶段已经生成完成，因此 BuildBatch 不会参与顶点计算，而是直接使用缓存结果。

二、排序阶段

系统会根据渲染顺序对所有元素进行排序。排序依据包括 Transform 层级、Canvas 排序参数以及渲染模式等因素。

排序的目的，是保证最终生成的批次在视觉上符合正确的覆盖关系。

三、分组阶段

在排序完成后，系统会根据材质与纹理状态对元素进行初步分组。这一阶段为后续的合批提供基础条件。

四、合批构建阶段

这是 BuildBatch 的核心步骤。系统会尝试将连续满足条件的 UI 元素合并到同一个批次中。

在实现上，多个 CanvasRenderer 的顶点数据会被拼接到同一顶点缓冲区中，同时重建索引数据，以保证几何结构正确。

该过程发生在 CPU 侧，因此会产生一定的内存拷贝与计算开销。

五、绘制指令生成阶段

当批次构建完成后，系统会为每一个批次生成对应的绘制指令，包括顶点缓冲区、索引缓冲区以及材质状态。

这些指令最终会被提交给底层渲染管线，由 GPU 执行实际绘制。

### 6\.4\.3 合批条件与中断机制

在 UGUI 中，并非所有 UI 元素都可以被合并。合批必须满足严格的条件。

常见的合批条件包括：

- 使用相同的材质

- 引用相同的纹理

- 具有一致的渲染状态

一旦在遍历过程中遇到不满足条件的元素，系统就会中断当前批次，并开启新的批处理。

这种“顺序扫描 \+ 条件中断”的机制，是 DrawCall 产生的根本原因。

需要特别注意的是，一些常见功能会直接导致批处理失败，例如：

- Mask 与 RectMask2D

- 不同的材质实例

- 动态修改纹理

- 使用不同的 Shader

这些因素都会打断批次连续性，从而增加 DrawCall 数量。

### 6\.4\.4 执行触发时机

Canvas\.BuildBatch 并不会在每一帧无条件执行。

只有当 Canvas 被标记为需要更新时，系统才会触发批处理重建。例如：

- UI 元素被标记为 Dirty

- 顶点数据发生变化

- 材质或纹理发生变化

- 层级结构发生改变

这种按需执行机制，可以有效避免不必要的 CPU 开销，是 UGUI 性能优化的重要基础。

### 6\.4\.5 多 Canvas 对批处理的影响

在多 Canvas 结构中，每一个 Canvas 都会独立执行一次 BuildBatch。

这意味着：

- Canvas 数量越多，批处理执行次数越多

- 不同 Canvas 之间无法共享批次

因此，拆分 Canvas 虽然可以降低单次更新范围，但也会增加整体 DrawCall 数量。

在实际项目中，需要在“减少重建成本”与“保持批处理连续性”之间进行权衡。

### 6\.4\.6 性能开销分析

Canvas\.BuildBatch 的性能开销主要集中在两个方面。

一、CPU 侧数据处理

包括顶点数据拼接、索引重建以及批次划分。

二、DrawCall 数量

批次划分越碎，DrawCall 数量越多，GPU 开销越高。

需要强调的是，BuildBatch 本身并不会直接影响 GPU 性能，但它决定了 GPU 将要执行多少次绘制调用。

因此，它是连接 CPU 开销与 GPU 开销的关键节点。

### 6\.4\.7 小结

Canvas\.BuildBatch 本质上是一个渲染数据整理器。它将前面所有分散的 UI 数据进行统一整合，并根据合批规则生成高效的渲染批次。

通过排序、分组与合批，BuildBatch 将多个 UI 元素转化为尽可能少的 DrawCall，从而提升整体渲染效率。

理解这一过程，是深入掌握 UGUI 渲染机制以及进行 UI 性能优化的核心基础。

## 6\.5 批处理准备阶段

在 Canvas\.BuildBatch 正式执行合批之前，UGUI 还会经历一个关键但容易被忽视的阶段，即批处理准备阶段。该阶段并不直接生成批次，而是对所有 UI 渲染数据进行预处理，为后续合批构建稳定且可预测的输入环境。

从执行流程来看，批处理准备阶段位于 Rebuild 完成之后、BuildBatch 执行之前。此时所有 UI 的布局结果与 Mesh 数据已经生成，但这些数据仍然分散在各个 CanvasRenderer 中，尚未形成统一的渲染序列。

### 6\.5\.1 阶段目标与作用

批处理准备阶段的核心目标，可以概括为三点。

一、统一渲染数据结构

将分散在各个 CanvasRenderer 中的数据整理为统一格式。

二、确定稳定渲染顺序

保证后续合批过程中不会破坏视觉叠加关系。

三、建立合批判断基础

提前对渲染状态进行分类与标记，提高合批效率。

从本质上看，这一阶段是 BuildBatch 的前置步骤，其输出结果将直接影响最终的 DrawCall 数量。

### 6\.5\.2 渲染数据收集

在准备阶段开始时，Canvas 会遍历其下所有 CanvasRenderer，提取每个 UI 元素的关键渲染信息。

这些信息主要包括：

- 顶点数据

- 材质引用

- 纹理资源

- 渲染相关状态

需要注意的是，这些数据在 Graphic 重建阶段已经生成完成，因此此处仅进行读取与整理，而不会发生新的计算过程。

这一过程的结果，是将分散的渲染数据汇总为一组可处理的输入集合。

### 6\.5\.3 渲染顺序确定

在数据收集完成后，系统会对所有 UI 元素进行线性排序。

排序依据主要包括：

- Transform 层级结构

- Canvas 的 sortingOrder

- Render Mode 所对应的渲染规则

- Canvas 嵌套关系

这一排序过程的核心目的，是确保渲染结果的正确性。

由于后续合批会将多个 UI 元素的顶点数据合并，一旦顺序出现错误，就会直接导致覆盖关系异常。因此，可以将该阶段理解为对渲染顺序的“锁定”。

排序完成后，所有 UI 元素会形成一条严格有序的渲染队列。

### 6\.5\.4 状态对齐与初步分组

在顺序确定之后，系统会对每个 UI 元素的渲染状态进行分析，以判断其是否具备合批条件。

关键判断因素包括：

- 材质是否一致

- 纹理是否相同

- Shader 及其参数状态

- 是否启用裁剪或其他特殊效果

在这一过程中，系统会对具有相同渲染状态的元素进行初步分组。

需要强调的是，这些分组并不是最终的批次划分，而是为 BuildBatch 提供快速判断依据，从而减少运行时的状态比较成本。

### 6\.5\.5 特殊状态处理

在实际 UI 系统中，存在一些会直接影响合批规则的特殊情况。

常见的包括：

- Mask 与 RectMask2D

- 不同的 Shader Pass

- Stencil 测试相关状态

- 裁剪区域变化

这些因素会导致渲染状态发生变化，从而打断批次连续性。

因此，在批处理准备阶段，系统会对这些特殊状态进行标记，并在渲染队列中进行隔离。这一处理可以避免在 BuildBatch 阶段频繁进行复杂判断。

### 6\.5\.6 渲染队列构建

经过上述步骤后，系统会将所有 UI 渲染数据整理为一条有序的渲染队列。

该队列中的每一个元素，通常包含以下信息：

- 顶点数据引用

- 材质与纹理信息

- 渲染顺序索引

- 状态标记

这一数据结构，本质上是 BuildBatch 的输入源。

后续所有的合批操作，都是基于这条渲染队列进行顺序扫描与条件判断。

### 6\.5\.7 对性能的影响

虽然批处理准备阶段不直接执行顶点合并，但它对性能的影响是决定性的。

其主要影响体现在两个方面。

一、合批效率上限

如果渲染队列中状态切换频繁，即使 BuildBatch 逻辑正确，也无法形成大规模批次。

二、CPU 处理成本

良好的数据组织可以减少后续阶段的判断与分支，从而降低整体开销。

例如，在 UI 层级中频繁插入不同材质或不同纹理的节点，会导致排序后状态不断变化，从而严重破坏批处理连续性。

这类问题的根源，通常并不在 BuildBatch 本身，而是在准备阶段的数据排列方式。

### 6\.5\.8 小结

批处理准备阶段本质上是一个渲染数据规范化过程。它将原本分散且不确定的 UI 渲染数据，整理为顺序稳定、状态明确的结构化输入。

虽然这一阶段不直接生成 DrawCall，但它决定了后续合批的可行性与效率，是 UI 渲染性能优化的源头环节。

理解这一阶段的作用，可以帮助开发者从 UI 结构设计层面提升渲染效率，而无需依赖底层代码修改。

## 6\.6 多 Canvas 组织策略

在 UGUI 的渲染体系中，Canvas 既是渲染提交的基本单位，也是 UI 更新与重建的边界。因此，Canvas 的组织方式，将直接影响 UI 系统的性能表现与结构稳定性。

多 Canvas 组织策略，本质上是在“重建范围”与“批处理效率”之间进行权衡的一种架构设计。

### 6\.6\.1 基本机制与设计前提

从机制上看，每一个 Canvas 都拥有独立的更新与批处理流程。

当某个 Canvas 内的 UI 元素发生变化时，仅会触发该 Canvas 的 Rebuild 与 BuildBatch，而不会影响其他 Canvas。这种更新隔离特性，是多 Canvas 优化的基础。

需要明确一个核心前提：Canvas 是重建的最小单位，而不是合批的最小单位。

拆分 Canvas 可以缩小更新范围，但同时也会打断批处理连续性。因此，Canvas 的划分必须建立在对更新频率与渲染成本的综合判断之上。

### 6\.6\.2 常见组织策略

在实际项目中，多 Canvas 通常采用以下几种组织方式。

一、动静分离

将频繁变化的 UI 与静态 UI 分离到不同 Canvas 中。

例如，将倒计时、血条、动态数值等内容独立出来，而将背景、装饰与框架保持在静态 Canvas 中。这样，当动态元素更新时，不会触发整个界面的重建。

二、局部隔离

在复杂 UI 结构中，将高频变化区域单独拆分为子 Canvas。

典型场景包括 ScrollRect 列表、动态生成的内容区域等。这些区域通常更新频率高且结构复杂，单独隔离可以显著降低整体更新成本。

三、层级分离

根据 UI 的显示层级进行划分，例如主界面层、弹窗层、提示层等。

这种划分方式不仅有助于管理渲染顺序，还可以避免高层 UI 的变化影响底层结构，从而提升系统稳定性。

### 6\.6\.3 子 Canvas 机制

在多 Canvas 结构中，子 Canvas（嵌套 Canvas）是一种常见实现方式。

子 Canvas 具备独立的批处理能力，会作为单独的批次构建单元存在。但与此同时，它仍然继承父 Canvas 的渲染模式与排序体系。

这种设计使子 Canvas 既能够隔离更新范围，又不会破坏整体 UI 的空间一致性。

需要注意的是，子 Canvas 会在内部形成新的批处理边界，因此其使用应当以“隔离高频变化”为目标，而非简单的结构拆分。

### 6\.6\.4 性能影响分析

多 Canvas 结构对性能的影响主要体现在两个方面。

一、DrawCall 数量增加

由于不同 Canvas 之间无法合批，即使使用相同材质与纹理，也会被拆分为多个批次。因此，Canvas 数量越多，理论上的 DrawCall 下限越高。

二、CPU 开销增加

每一个 Canvas 在更新时都需要独立执行 BuildBatch。当 Canvas 数量较多时，批处理构建的 CPU 成本会明显上升。

因此，多 Canvas 并非无成本优化，其收益取决于是否有效减少了不必要的重建。

### 6\.6\.5 设计决策原则

在实际开发中，可以基于以下原则进行 Canvas 划分。

一、优先隔离高频变化区域

变化越频繁的 UI，越应该独立为单独 Canvas。

二、避免过度拆分静态内容

静态 UI 通常不需要拆分，否则只会增加 DrawCall。

三、控制 Canvas 总数量

在满足更新隔离需求的前提下，尽量减少 Canvas 数量，以保持批处理效率。

四、保持层级结构清晰

Canvas 的划分应与 UI 结构逻辑一致，避免出现混乱的嵌套关系。

### 6\.6\.6 常见错误用法

在实际项目中，多 Canvas 使用不当往往会导致性能问题。

常见错误包括：

- 将每个 UI 元素都拆分为独立 Canvas

- 在静态界面中大量使用子 Canvas

- 频繁创建与销毁 Canvas

- 忽略材质统一导致批处理失效

这些问题通常会导致 DrawCall 激增或 CPU 开销上升，从而抵消多 Canvas 带来的优化收益。

### 6\.6\.7 小结

多 Canvas 组织策略本质上是一种局部更新优化手段。它通过人为划分更新边界，使 UI 系统能够以更小粒度执行重建，从而提升整体性能稳定性。

合理的 Canvas 设计，应在更新成本与渲染成本之间取得平衡，并结合具体业务场景进行结构划分。

只有在深入理解 Canvas 更新机制与批处理流程的基础上，才能制定出高效且可维护的 UI 架构方案。

## 6\.7 CanvasScaler 与适配

在 UGUI 系统中，Canvas 负责 UI 的组织与渲染，而 CanvasScaler 则负责解决不同分辨率设备下 UI 的显示一致性问题。两者分别对应“如何绘制”与“如何适配”，共同构成完整的 UI 表现体系。

从本质上看，CanvasScaler 并不会改变 UI 的结构或布局规则，而是通过统一的缩放策略，在设计分辨率与实际屏幕之间建立映射关系，从而保证 UI 在不同设备上的视觉一致性。

### 6\.7\.1 缩放机制的本质

CanvasScaler 的核心作用，是在 UI 坐标体系与屏幕像素之间插入一层缩放变换。

在 UI 系统内部，所有 RectTransform 的计算结果，都是基于设计尺寸得到的逻辑坐标。而在最终渲染阶段，这些坐标会乘以一个统一的缩放因子，映射到实际屏幕像素空间。

可以将这一过程理解为：设计坐标 → 缩放变换 → 屏幕坐标

这一缩放因子由 CanvasScaler 根据当前分辨率与配置策略计算得到。

需要强调的是，这一过程发生在渲染之前，因此不会影响 Layout 系统的计算结果，而只影响最终显示。

### 6\.7\.2 三种适配模式

CanvasScaler 提供三种主要的适配模式，以满足不同应用场景。

一、Constant Pixel Size

在该模式下，UI 完全以像素为单位进行显示，不随屏幕分辨率变化。

这意味着在高分辨率设备上，UI 会显得更小；在低分辨率设备上，则会显得更大。该模式适用于对像素精度要求较高，但不强调跨设备一致性的场景。

二、Scale With Screen Size

这是最常用的适配模式。

在该模式下，开发者需要指定一个参考分辨率，系统会根据当前屏幕尺寸与参考分辨率之间的比例，计算缩放因子。

其中，Match Width Or Height 参数用于控制缩放依据：

- 当值为 0 时，以宽度为基准

- 当值为 1 时，以高度为基准

- 介于两者之间时，对宽高缩放结果进行插值

这种机制可以在不同屏幕比例下平衡 UI 的拉伸与压缩问题。

三、Constant Physical Size

该模式基于物理单位（如英寸或毫米）进行适配，并依赖设备 DPI 计算缩放比例。

理论上可以保证 UI 在不同设备上的物理尺寸一致，但由于设备 DPI 数据通常不准确，因此在实际项目中使用较少。

### 6\.7\.3 缩放因子的计算模型

在 Scale With Screen Size 模式下，缩放因子的计算是整个适配机制的核心。

设参考分辨率为Wref，Href，当前分辨率为 W，H，则可以分别计算宽度与高度方向的缩放比。

$S_w=\frac{W}{W_{ref}}，S_h=\frac{H}{H_{ref}}$

最终缩放因子由 Match 参数控制，在宽高缩放之间进行插值。

$s=(1-t)*s_w+t*s_h$

其中，t表示 Match Width Or Height 的取值。

这一计算方式保证了 UI 在不同分辨率与比例下具有可控的缩放行为。

### 6\.7\.4 与 Layout 系统的关系

CanvasScaler 不参与 Layout 计算，是理解其行为的关键。

Layout 系统始终基于未缩放的逻辑坐标进行计算，而 CanvasScaler 只在最终阶段对结果进行统一缩放。

这意味着：

- 布局结果不会因分辨率变化而改变

- 显示尺寸会随着缩放因子变化

因此，如果 UI 布局出现错位问题，通常原因在 Layout 系统，而不是 CanvasScaler。

### 6\.7\.5 多 Canvas 下的适配策略

在多 Canvas 结构中，每个 Canvas 都可以独立配置 CanvasScaler。

这使得不同 UI 层可以采用不同的适配策略。例如：

- 主界面使用 Scale With Screen Size

- 世界空间 UI 使用 World Space，不进行缩放

- 特殊 UI 使用固定像素模式

这种灵活性，使 UI 系统可以同时兼顾一致性与特殊表现需求。

### 6\.7\.6 对系统的影响

CanvasScaler 本身的性能开销较低。缩放因子的计算通常只在初始化或分辨率变化时执行，而不会参与每帧更新。

但其影响是全局性的：

- 所有 UI 显示结果都会受到缩放因子的影响

- 错误的适配策略会导致整体 UI 失衡

- 精确像素依赖逻辑可能被破坏

因此，在设计 UI 系统时，应优先确定统一的适配策略，再进行具体布局设计。

### 6\.7\.7 小结

CanvasScaler 本质上是一个坐标缩放系统。它通过在设计坐标与屏幕像素之间建立映射关系，使 UI 能够在不同分辨率设备上保持一致的视觉表现。

需要明确的是，它解决的是“显示尺度问题”，而不是“布局问题”。只有在正确理解这一边界的前提下，才能合理使用 CanvasScaler，构建稳定且可适配的 UI 系统。

## 6\.8 子 Canvas 机制

在 UGUI 系统中，Canvas 不仅可以作为 UI 的根节点存在，还可以嵌套在层级结构中形成子 Canvas。子 Canvas 的引入，使 UI 系统具备了更细粒度的更新控制能力，同时也在渲染层面引入了新的批处理边界。

从系统角度来看，子 Canvas 并不是简单的层级节点，而是一种“局部渲染上下文”的划分方式。

### 6\.8\.1 子 Canvas 的本质

当在某个 UI 节点上添加 Canvas 组件时，该节点及其所有子节点会被划分为一个独立的渲染单元。

这一单元具备以下特性：

- 拥有独立的更新边界

- 拥有独立的批处理流程

- 拥有独立的 DrawCall 生成过程

因此，可以将子 Canvas 理解为一个“局部渲染边界”。它将原本属于同一 Canvas 的 UI 数据，划分为多个独立处理区域。

这一划分直接影响 UI 的更新范围与批处理结构。

### 6\.8\.2 更新隔离机制

在没有子 Canvas 的情况下，任意一个 UI 元素发生变化，都会导致整个 Canvas 执行重建与批处理。

引入子 Canvas 后，更新过程会发生变化：

- Dirty 标记只会向上作用到最近的 Canvas 边界

- CanvasUpdateRegistry 只会调度受影响的 Canvas

- BuildBatch 仅在对应 Canvas 内执行

这一机制使 UI 更新可以被限制在局部区域，从而显著降低重建成本。

从执行流程上看，子 Canvas 与根 Canvas 并无本质区别，它同样参与完整的更新与渲染流程，只是作用范围被限制在自身子树内。

### 6\.8\.3 渲染顺序与排序体系

子 Canvas 虽然独立执行批处理，但其渲染顺序仍然受到整体 Canvas 体系的控制。

默认情况下，子 Canvas 会继承父 Canvas 的排序规则，包括：

- Sorting Layer

- Order in Layer

- 层级顺序

这意味着，子 Canvas 并不会打破 UI 的整体绘制顺序，而是在既定顺序下独立生成批次。

这种设计保证了在进行局部优化时，不会破坏全局视觉结果。

### 6\.8\.4 overrideSorting 机制

Canvas 提供了 overrideSorting 选项，用于控制子 Canvas 是否独立参与排序。

当 overrideSorting 关闭时，子 Canvas 完全遵循父 Canvas 的排序体系。

当 overrideSorting 开启时，子 Canvas 可以指定独立的 Sorting Layer 与 Order in Layer，从而脱离父级排序控制。

需要注意的是，overrideSorting 只影响“排序体系”，而不会改变子 Canvas 的批处理独立性。

换言之，无论是否开启 overrideSorting，子 Canvas 都会作为独立批处理单元存在。

### 6\.8\.5 合批阻断机制

子 Canvas 的一个重要特性，是会阻断跨 Canvas 的批处理。

在 BuildBatch 阶段，系统只会在同一个 Canvas 内进行顺序扫描与合批判断，而不会跨越 Canvas 边界。

这意味着：

- 不同 Canvas 之间无法共享批次

- 即使材质与纹理完全相同，也不会被合并

这一行为并非优化限制，而是系统设计结果。

因为每个 Canvas 都会独立构建渲染数据结构，其内部批次在生成后已经被封装为独立的绘制单元，无法再参与其他 Canvas 的合批过程。

### 6\.8\.6 使用场景分析

在实际项目中，子 Canvas 常用于以下几类场景。

一、高频更新区域

例如滚动列表、动态数值、实时变化 UI 等。通过子 Canvas 可以限制更新范围，避免整个界面频繁重建。

二、复杂布局隔离

在包含 LayoutGroup 或 ContentSizeFitter 的结构中，子 Canvas 可以阻断布局变化向外传播，从而提升系统稳定性。

三、特效隔离

带有 Mask、动画或特殊 Shader 的 UI 元素，往往会打断合批。将其放入子 Canvas，可以避免影响其他 UI。

### 6\.8\.7 使用成本与限制

子 Canvas 虽然提供了更新隔离能力，但同时也带来一定成本。

主要包括：

- DrawCall 数量增加

- 批处理被拆分

- BuildBatch 执行次数增加

当子 Canvas 数量过多时，CPU 与 GPU 开销都会明显上升。

此外，过深的 Canvas 嵌套结构，也会增加系统复杂度，使渲染顺序与更新关系变得难以维护。

因此，子 Canvas 的使用应遵循“必要隔离”的原则，而非盲目拆分。

### 6\.8\.8 小结

子 Canvas 机制本质上是一种局部渲染边界划分方式。它通过将 UI 系统拆分为多个独立执行单元，实现更新范围的精细控制。

其核心价值在于降低不必要的重建成本，但代价是批处理被拆分，从而增加 DrawCall 数量。

只有在理解其更新隔离机制与合批阻断原理的基础上，才能在性能与结构之间取得合理平衡。
